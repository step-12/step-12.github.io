      Git basic commands

      September 22, 2026
      Git, Basic Commands

      In the previous post, you used gacp to send your changes to GitHub, without worrying about what it does.

      Time to look inside.

      The name gives it away:

      gacp
 │││└─ push
 ││└── commit
 │└─── add
 └──── git

      gacp runs add, commit and push for you, one after the other.

      In this post, we will go through each of them by hand.

      The loop#

      Every time you change your code, you go through the same loop:

              ┌──────────────┐
        │  Look at     │  What changed?
        │  your changes│
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │     Add      │  Tell Git which changes to include
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │    Commit    │  Record them in your local history
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │     Push     │  Send your history to the remote
        └──────┬───────┘
               │
               ▼
      write more code, repeat

      Two places are involved:

      local   →  your computer
remote  →  GitHub

      The first three steps happen on local. Only the last one touches remote.

      Let’s go through each step. We will use a small file, hello.js, inside a repository you have already set up:

      console.log("Hello");

      Change it:

      console.log("Hello Odyssey");

      Git doesn’t record this on its own. Let’s walk through the loop.

      Look at your changes#

      Before anything else, you want to know what Git sees.

      Which files did I change? Is anything already selected? Is there something I forgot?

      The command for this is:

      git status

      It answers one question:

      What is the current state of my work?

      Run it right after changing hello.js:

      On branch main
Changes not staged for commit:
        modified:   hello.js

no changes added to commit

      Read it like this:

      modified:   hello.js
      ↓
Git noticed that hello.js changed
      ↓
but it is not selected for the next commit yet

      git status doesn’t change anything. It only tells you what Git sees, so it is safe to run as often as you like.

      Add#

      Add is you telling Git what changes to include.

      You might have changed three files, but only two of them belong together. With add, you choose exactly which changes go into the next commit.

      Nothing is recorded yet. You are only selecting.

      Your changes
     │
     │ add: "these ones"
     ▼
Selected changes

      The command is:

      git add hello.js

      You are telling Git: “include the changes in hello.js in my next commit.”

      Run git status again:

      On branch main
Changes to be committed:
        modified:   hello.js

      The wording changed from Changes not staged for commit to Changes to be committed. That is how you know the add worked.

      The selected changes are called the staging area.

      Choosing what to add#

      Imagine you changed three files:

      hello.js
math.js
login.js

      Suppose you only want the math.js change in your next commit:

      git add math.js

      The changes from hello.js and login.js are not included. That is the point of add: you choose what goes into the next commit.

      To select everything you changed:

      git add .

      Commit#

      Commit records the selected changes locally, and updates your history locally.

      After a commit, your history has one more entry. That entry holds the changes you selected, along with a message describing them.

      Everything still lives on your computer. GitHub doesn’t know about it yet.

      Selected changes
     │
     │ commit
     ▼
Local history  ●──●──●──●  ← new entry

      The command is:

      git commit

      Git opens a text editor for you to write a message. Save the file and close the editor, and Git creates the commit.

      Run git status once more:

      On branch main
Your branch is ahead of 'origin/main' by 1 commit.

nothing to commit, working tree clean

      The commit message#

      Every commit needs a message that describes what it contains.

      In the editor, write something like:

      improve greeting

Add the name and punctuation to the greeting,
so it reads "Hello, Odyssey!" instead of "Hello".

      The message has two parts:

      improve greeting                      ← short summary (first line)
                                      ← blank line
Add the name and punctuation ...      ← longer description (optional)
      • The first line is a short summary of the change. This is what git log shows.
      • The body, after a blank line, explains the what and why in more detail. It is optional, but useful when the summary alone isn’t enough.

      A history of commits with no messages tells you nothing. A good message tells you what a commit did without opening it.

      Use VS Code to write commit messages#

      The editor Git opens by default depends on your machine, and it is often vim, which can be confusing if you haven’t used it before.

      Let’s tell Git to use VS Code instead.

      Run:

      git config --global core.editor "code --wait"

      Now run git commit again. VS Code opens a tab with the commit message file. Write your message, save it with Cmd+S, and close the tab. Git creates the commit.

      If you see code: command not found, open VS Code, press Cmd+Shift+P, and run Shell Command: Install ‘code’ command in PATH. Then try again.

      This is a one-time setup. You will not need to run it again.

      Looking at your history#

      Each commit you make becomes an entry in your local history. To look at it:

      git log

      You will see something like:

      commit 8f31a2...
Author: Charan
Date:   ...

    improve greeting

commit 2c91bd...
Author: Charan
Date:   ...

    handle empty name

commit 7a21ef...
Author: Charan
Date:   ...

    add greet function

      Don’t worry about every line yet. At this level, focus on:

      git log
    ↓
show me the commits, newest first

      Push#

      Push sends your local history to the remote.

      Until you push, your new commits exist only on your computer. After you push, they are on GitHub too, and your mentors and peers can see them.

      Local history   ●──●──●──●
                          │
                          │ push
                          ▼
Remote history  ●──●──●──●

      Only commits are sent. A change you never added and committed has nothing to push.

      The command is:

      git push

      After pushing, run git status:

      On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean

      up to date with 'origin/main' means local and remote now have the same history.

      Putting it together#

      The loop, as commands:

              ┌──────────────┐
        │  git status  │  What changed?
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │   git add    │  Choose what goes in the commit
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │  git commit  │  Record it locally
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │  git push    │  Send it to the remote
        └──────┬───────┘
               │
               ▼
      write more code, repeat
      git status
git add hello.js
git commit
git push

      A few habits that make the loop work:

      • Run git status before git add, to see what you are about to select.
      • Run git status after git commit, to confirm the working tree is clean.
      • Use git log any time you want to look back at your history.

      gacp "improve greeting" is the same loop, minus the git status, in one line.

      The mental model#

       local                                          remote
 ─────                                          ──────

 Your files
     │
  git add
     │
     ▼
 Staging area
     │
 git commit
     │
     ▼
 Local history  ───────── git push ───────────▶  Remote history

      with git status and git log as the two ways of looking at where things stand:

      git status  →  what is the state of my work right now?
git log     →  what does my recorded history look like?
