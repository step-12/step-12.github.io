    Process, Terminals, Shells

    September 10, 2026
    Shell, Terminal, Process

    Process#

    When your computer starts, the kernel is one of the first pieces of the operating system to start running. The kernel is responsible for managing the computer: its memory, CPU, devices, files and, importantly, the programs that are running.

    But what does it mean for a program to be running?

    From Program to Process#

    A program starts life as a file on a storage device. When you install an application, its code is sitting on your disk or SSD.

    When you open the application, the operating system copies the parts it needs into RAM and asks the kernel to start executing its code.

    That running program is a process.

    So:

    program on disk
      ↓
    loaded
      ↓
     RAM
      ↓
   executing
      ↓
    process

    You can see this happening on a Mac without writing any code.

    Open Activity Monitor. You can find it by opening Spotlight with ⌘ Space and searching for Activity Monitor.

    Activity Monitor shows you the processes currently running on your computer. Some of them are applications you recognise. Many others are background processes that you have never seen before.

    Leave Activity Monitor open for a moment and open another application. Watch the list. You should see new processes appear.

    Close the application again. Its processes will eventually disappear.

    There is much more going on here than a list of applications, though. Processes can start other processes.

    PIDs#

    Every process has a number called a Process ID, or PID.

    Look at Activity Monitor again. One of the columns is PID. This number identifies a particular process.

    For example:

    Application       PID
---------------------
Safari            3812
Calculator        4271

    The numbers aren’t names for the programs. They are identifiers assigned to individual processes.

    We can explore this relationship more easily from the command line.

    A First Look at the Command Line#

    For the experiments in this section, we need a way to type commands to the operating system.

    On a Mac, open Terminal. You can find it with Spotlight in the same way you found Activity Monitor.

    You will see a window containing something that looks roughly like this:

    your-computer ~ %

    Don’t worry about what all of this means yet. For now, think of Terminal as a place where we can type commands and see their results. We’ll come back to exactly what a terminal and a shell are later.

    Type:

    pstree

    and press Enter.

    pstree displays processes as a tree. You may see something like:

    launchd
 ├── Terminal
 │    └── zsh
 │         └── pstree
 └── ...

    Your output will be different. That’s fine.

    Notice something interesting: pstree itself appears in the tree.

    That’s because pstree is a program too. When you typed pstree, the shell started a new process to run it.

    This gives us our first useful picture of processes:

    shell
  └── pstree

    The shell is the parent and pstree is its child.

    Child Processes#

    Processes can create other processes.

    For example:

    shell
 ├── program A
 └── program B

    Here the shell started two programs. Those programs are child processes of the shell.

    A process can itself start more processes:

    shell
 └── program A
      ├── worker
      └── worker

    This is why pstree is useful. Instead of seeing processes as a flat list, we can see their relationships.

    Run pstree a few times. Then open another application and run it again. Look at what changes.

    The exact output will depend on your computer. The important thing is the shape of the tree.

    Signals#

    Processes can also receive signals.

    A signal is a notification sent to a process telling it that something has happened or asking it to perform some action.

    For example, when you run a program in Terminal and press Ctrl-C, you are sending it a signal asking it to stop.

    You can also send a signal using the process’s PID:

    kill 4271

    Here 4271 is the PID of the process you want to signal.

    Despite its name, kill does not necessarily mean “destroy this process immediately.” It is a command for sending signals to processes. Different signals have different meanings.

    We’ll see more of this when we start running programs that don’t finish immediately.

    Zombie Processes#

    There is one final oddity worth seeing.

    A child process can finish running while its parent process is still alive. When this happens, the parent needs to collect some information about the child’s termination.

    If the child has finished but its parent hasn’t yet collected that information, the child can temporarily appear as a zombie.

    A zombie process isn’t actually running anymore. Its work is finished. What remains is a small amount of information that the operating system keeps around for its parent.

    You may eventually encounter zombies when looking at process trees. Don’t confuse one with a process that is consuming CPU in the background: a zombie has already stopped running.

    At this point, the important picture is:

            process
        /     \
   child       child
   /   \
child  child

    Processes form relationships. They have PIDs so we can identify them, and they can communicate with the operating system through signals.

    And, as we have just seen, even the commands we type are themselves programs that become processes when we run them.

    Terminals#

    In the previous section, we used Terminal to run pstree.

    But what exactly was Terminal?

    It is tempting to think of the black window with the blinking cursor as the command line. It is actually a little more complicated than that.

    A terminal is a way of interacting with a computer by typing and receiving text.

    Today, a terminal is usually an application running inside our graphical desktop. In this section, we’ll see why that is the case.

    A Very Short History#

    The story starts before computers had screens.

    Early computers were large, expensive machines shared by many people. Users needed some way to communicate with them. One of the earliest solutions was essentially a typewriter connected to a computer.

    You typed something. The computer received the characters. It sent characters back. The terminal printed them.

    These machines were known as teletypes or teleprinters. This is where the abbreviation tty, which you may encounter later, comes from: Teletype.

    The idea was simple:

     computer
    ↕
characters
    ↕
terminal
    ↕
 person

    The terminal wasn’t doing the actual computing. The computer was.

    Over time, paper was replaced by screens. Terminals became things like the famous DEC VT100: a keyboard and screen connected to a computer, communicating by sending and receiving characters.

    Eventually, computers became small and powerful enough to sit on our desks. There was no longer much point in buying a separate physical terminal just to talk to your own computer.

    So we wrote programs that pretended to be terminals.

    These programs are called terminal emulators.

    The terminal window you open on your Mac is one of these.

    A Terminal Emulator#

    Open Ghostty.

    Ghostty is a terminal emulator. It provides the part of the experience that an old physical terminal used to provide: a place to type characters and a place to display the characters coming back from the computer.

    Ghostty itself isn’t the thing interpreting the commands you type. That’s the job of another program, called a shell, which we’ll meet in the next section.

    For now, a useful mental model is:

    you
 ↓
Ghostty
 ↓
shell
 ↓
program

    When you type something, the keystrokes travel through this system. When the program produces output, that output travels back and Ghostty displays it on your screen.

    This is the basic idea behind a modern terminal.

    Why Do We Still Use Terminals?#

    If computers have had graphical interfaces for decades, why are we still typing commands?

    Because typing a command is often a very convenient way to tell a computer exactly what you want.

    For example:

    pstree

    asks the computer to show us a process tree.

    A graphical application would need to provide a button, menu or other interface for every operation it supports. A command-line program can expose the same functionality through a short command.

    Terminals are particularly useful for programmers and system administrators because they make it easy to:

    • run programs
    • inspect files
    • manipulate files
    • automate repetitive tasks
    • install software
    • connect to other computers

    That last one is particularly important.

    A server in a data centre might not have a monitor, keyboard or graphical desktop at all. We can connect to it over a network and use a terminal to interact with it.

    The terminal therefore isn’t just a relic from the days of giant computers. It is still one of the most useful ways of interacting with modern computers.

    Some Terminals#

    Ghostty is the terminal we’ll use in this course. It is fast, cross-platform and designed to behave like a native application on macOS and Linux. It also supports tabs, splits and other conveniences that make working with multiple terminal sessions easier.

    There are many other terminal emulators, including:

    • Terminal.app — Apple’s built-in terminal on macOS
    • iTerm2 — a popular macOS terminal
    • Kitty — a fast, feature-rich terminal
    • Alacritty — a GPU-accelerated terminal focused on simplicity and performance

    They look different and have different features, but they all perform essentially the same basic job: they provide a terminal interface for programs running on your computer.

    And this brings us back to processes.

    When you opened Ghostty, you didn’t just open a window. You started a program. That program then started a shell, which in turn can start other programs.

    We can see that entire chain in our process tree.

    Ghostty
  └── shell
       └── pstree

    There are three different things here.

    Ghostty is the terminal.

    The shell is the program that interprets commands.

    pstree** is a command that runs a program.**

    We’ll look at the shell next.

    Shell#

    In the previous section, we saw that Ghostty is a terminal. It gives us a place to type and a place to see the computer’s response.

    But Ghostty isn’t actually the thing that understands what we type.

    That job belongs to the shell.

    Terminal ≠ Shell#

    When you open Ghostty, you are opening a terminal emulator. Ghostty provides the interface through which we interact with another program.

    That other program is the shell.

    On our machines, that shell is zsh.

    The relationship looks like this:

    you
 ↓
Ghostty
 ↓
zsh
 ↓
other programs

    Ghostty deals with the terminal. zsh deals with the commands.

    You can actually see this in our process tree:

    Ghostty
  └── zsh
       └── pstree

    Ghostty is one process. zsh is another process running inside it. When we type pstree, zsh can start yet another process to run pstree.

    The three are different things.

    What Is a Shell?#

    A shell is a program that interprets commands.

    If you’ve been following along with Sprint, this idea should feel familiar.

    Sprint is essentially an interpreter. It reads an instruction, works out what that instruction means, carries it out, and then moves on to the next instruction.

    A shell does something remarkably similar.

    The difference is that instead of reading instructions from a map, the shell reads them from us.

    We can think of its main loop like this:

    print a prompt
      ↓
read what the user typed
      ↓
figure out what it means
      ↓
do it
      ↓
print a prompt
      ↓
read again
      ↓
...

    In Sprint, instruction 9 means “stop”. A shell doesn’t normally reach the end after one instruction. It finishes one command and comes back asking for another.

    Commands#

    Try this in Ghostty:

    ls

    You should see a list of files and directories.

    What happened?

    First, zsh read the characters you typed:

    ls

    It then worked out what ls means and ran it.

    The command itself has a simple structure:

    command    arguments
   ↓          ↓
  ls       ...

    For example:

    ls -l ~/Downloads

    Here:

    • ls is the command name
    • -l is an argument
    • ~/Downloads is another argument

    Arguments give the command additional information about what we want it to do.

    This is somewhat like the instructions in Sprint.

    In Sprint:

    1 10 20 30

    The 1 tells us what operation to perform, while the other numbers provide information needed by that operation.

    A shell command has a similar idea:

    ls -l ~/Downloads

    ls tells the shell which command we want, while the remaining pieces provide information to that command.

    Does the Shell Do Everything?#

    Not quite.

    This is one of the most important things to understand about a shell.

    Some commands are built into the shell itself. Others are separate programs that the shell starts.

    Try:

    pwd

    Then:

    ls

    Both look like commands. But they don’t necessarily work in the same way.

    ls is a separate program. When zsh encounters it, zsh finds the program and starts it as a new process.

    We can see this happening with pstree.

    Run:

    pstree

    You’ll see something resembling:

    Ghostty
  └── zsh
       └── pstree

    The pstree process exists while the command is running. When it finishes, that process disappears.

    The shell remains.

    Ghostty
  └── zsh

    This is the difference between the shell interpreting a command and the shell launching another program.

    Built-in Commands#

    Some commands need to be handled by the shell itself.

    Try:

    cd ..

    cd means “change directory.”

    This cannot simply be handled by starting another program.

    Why?

    Because the shell itself needs to change its current directory.

    Imagine zsh did this:

    zsh
  └── cd

    The cd program could change its directory and then finish. But zsh would still be sitting in its original directory.

    Instead, cd is built into the shell. zsh handles it itself.

    This gives us two broad categories:

                     command
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
     shell handles it     shell launches
                           another process
          │                   │
         cd                  ls

    This distinction is useful because a shell is not simply a collection of programs. It is itself a program that understands some commands and knows how to launch other programs.

    Many Shells#

    zsh is not the only shell.

    There are many different shells, just as there are many different terminal emulators.

    Some you may encounter are:

    • zsh — the shell we use
    • Bash — one of the most widely used shells
    • fish — designed to be particularly friendly and interactive
    • sh — a very old and influential shell

    They all serve the same basic purpose: they interpret commands and provide a way for us to interact with the operating system.

    They differ in their features, syntax and behaviour.

    For our purposes, we’ll use zsh.

    Back to Sprint#

    There is a useful way to think about everything we’ve seen so far.

    Sprint takes instructions and interprets them:

    instruction
     ↓
Sprint
     ↓
operation

    A shell takes commands and interprets them:

    command
   ↓
 zsh
   ↓
operation or another process

    But there is one enormous difference.

    Sprint’s instructions were designed specifically for Sprint. We wrote the interpreter and defined what instructions like 1, 3, 5 and 9 meant.

    A shell lives in a much bigger world.

    Its commands can cause the operating system to perform useful work, and many of those commands are actually separate programs.

    So when you type:

    ls -l ~/Downloads

    you aren’t asking Ghostty to list some files.

    You’re typing characters into a terminal. Ghostty passes those characters to zsh. zsh interprets them, finds the ls program, and starts a new process with the arguments -l and ~/Downloads.

    you
 ↓
Ghostty
 ↓
zsh
 ↓
ls -l ~/Downloads
 ↓
ls process
 ↓
output
 ↓
zsh
 ↓
Ghostty

    The terminal gives us the window.

    The shell understands our commands.

    The processes do the work.
