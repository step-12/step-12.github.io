    Objects part 2

    September 28, 2026
    Javascript, Objects

    Visualise it#

    At this point, it can be useful to stop reading and experiment with a visualiser.

    Try entering small examples such as:

    const a = {
  x: 10,
};

const b = a;

b.x = 20;

    Watch what happens when a and b refer to the same object.

    Then try:

    let a = {
  x: 10,
};

let b = a;

b = {
  x: 20,
};

    Pay attention to the difference.

    The visualiser is not a substitute for understanding the code.

    Use it to test your mental model.

    Mutation and reassignment#

    We have just seen two different operations.

    First:

    b.x = 20;

    This changes the object.

    We call this modifying or mutating the object.

    Second:

    b = {
  x: 20,
};

    This does something different.

    It makes b refer to a new object.

    Consider:

    let a = {
  x: 10,
};

let b = a;

b = {
  x: 20,
};

    How many objects are there now?

    There are two.

    Originally:

    a ──────┐
        ▼
     ┌───────┐
     │ x: 10 │
     └───────┘
        ▲
        │
b ──────┘

    After:

    b = {
  x: 20,
};

    we have:

    a ───────────► ┌───────┐
               │ x: 10 │
               └───────┘

b ───────────► ┌───────┐
               │ x: 20 │
               └───────┘

    The assignment changed the reference held by b.

    It did not change the original object.

    So:

    a.x;

    is:

    10

    while:

    b.x;

    is:

    20

    This distinction is extremely important.

    Remember these two#

    b.x = 20;

    means:

    Change the object.

    Whereas:

    b = {
  x: 20,
};

    means:

    Make b refer to another object.

    These are not the same operation.

    What does const mean now?#

    Let’s revisit const.

    const person = {
  name: "Asha",
};

    We can do:

    person.name = "Ravi";

    because we are changing the object.

    But:

    person = {};

    does not work because we are trying to make person refer to another object.

    So const is about the reference held by the variable.

    It does not make the object itself immutable.

    This is why you should not think:

    “const means this thing can never change.”

    Instead think:

    “const means this variable cannot be reassigned.”

    That is a much more useful mental model.

    Objects and function parameters#

    Now we can return to functions.

    Consider:

    const person = {
  name: "Asha",
  age: 20,
};

function birthday(person) {
  person.age = person.age + 1;
}

birthday(person);

    What is:

    person.age;

    after the function call?

    Predict first.

    Then run it.

    You should get:

    21

    Why?

    When we call:

    birthday(person);

    the parameter person refers to the same object as the variable outside the function.

    You can imagine:

    outside:

person ───────────────┐
                      ▼
                  ┌───────────┐
                  │ age: 20   │
                  └───────────┘

inside birthday():

person ───────────────┘

    There are two variables called person.

    They are in different scopes.

    But they refer to the same object.

    So when the function does:

    person.age = 21;

    it changes that object.

    When the function finishes, the caller can see the change.

    But what if the function reassigns the parameter?#

    Now try this:

    const person = {
  name: "Asha",
  age: 20,
};

function birthday(person) {
  person = {
    name: person.name,
    age: person.age + 1,
  };
}

birthday(person);

person.age;

    What do you expect?

    You might think the age becomes 21.

    But it remains:

    20

    Why?

    Inside the function, the parameter person is a local variable.

    Initially, it refers to the original object.

    Then this line:

    person = {
  name: person.name,
  age: person.age + 1,
};

    makes the local parameter refer to a new object.

    It does not make the caller’s variable refer to the new object.

    You can imagine:

    Before reassignment:

caller:
person ───────────────┐
                      ▼
                  ┌───────────┐
                  │ age: 20   │
                  └───────────┘
                      ▲
                      │
function parameter ───┘

    After reassignment:

    caller:
person ───────────────► ┌───────────┐
                        │ age: 20   │
                        └───────────┘


function parameter ────► ┌───────────┐
                         │ age: 21   │
                         └───────────┘

    The caller still refers to the original object.

    The function’s parameter now refers to another object.

    This is why it is important to distinguish:

    changing an object

    from:

    changing what a variable refers to

    What if we return the new object?#

    Now change the function:

    function birthday(person) {
  person = {
    name: person.name,
    age: person.age + 1,
  };

  return person;
}

    Now:

    const person = {
  name: "Asha",
  age: 20,
};

const olderPerson = birthday(person);

    What is:

    person.age;

    ?

    What is:

    olderPerson.age;

    ?

    Predict before running the code.

    You should get:

    person.age       → 20
olderPerson.age  → 21

    The function created a new object.

    It made its local parameter refer to that object.

    Then it returned that object.

    The caller stored the returned reference in olderPerson.

    This is a useful pattern:

    old object
    │
    ├── person
    │
    ▼

function creates a new object

    │
    ▼

new object
    │
    └── olderPerson

    The original object was not modified.

    A good practice#

    There are two ways we could write our birthday function.

    We could modify the object:

    function birthday(person) {
  person.age = person.age + 1;
}

    Or we could create and return another object:

    function birthday(person) {
  return {
    name: person.name,
    age: person.age + 1,
  };
}

    Both are possible.

    There are situations where modifying an object is exactly what we want.

    But as a general practice:

    Prefer not to modify objects that are passed into a function unless there is a good reason to do so.

    Why?

    Because a function that changes an object has a side effect.

    Someone calling:

    birthday(person);

    needs to know that person has been changed.

    Compare that with:

    const olderPerson = birthday(person);

    Here, the function produces a new value.

    The original person remains as it was.

    This is not an absolute rule.

    You will encounter perfectly reasonable programs where functions intentionally modify objects.

    But when you are designing your own functions, it is worth asking:

    Does this function need to change the object it was given?

    If the answer is no, consider returning a new value instead.

    Objects as lookups#

    So far, we have mostly used objects to model things.

    A person:

    const person = {
  name: "Asha",
  age: 20,
};

    A point:

    const point = {
  x: 10,
  y: 20,
};

    But objects have another useful purpose.

    They can be used as lookup tables.

    Remember:

    const capitals = {
  India: "New Delhi",
  France: "Paris",
  Japan: "Tokyo",
};

    We can ask:

    capitals["India"];

    and get:

    "New Delhi"

    We can put the country in a variable:

    const country = "Japan";

capitals[country];

    and get:

    "Tokyo"

    The object is now acting like a little table:

    country    capital
-------    -------
India      New Delhi
France     Paris
Japan      Tokyo

    This is a different way of thinking about objects.

    We are not necessarily modeling one particular “thing”.

    We are saying:

    Given this value, what other value is associated with it?

    Try creating your own lookup object.

    For example:

    const days = {
  Monday: 1,
  Tuesday: 2,
  Wednesday: 3,
};

    Then:

    const day = "Tuesday";

days[day];

    What do you get?

    Objects you have already been using#

    There is one more connection worth making.

    You have already used:

    require(...)

    You have seen things like:

    const r = require("raylib");

    You can think of require as giving you the value that another module exported.

    If that exported value is an object, then the value returned by require is an object.

    That means you can write:

    something.name;

    or:

    something["name"];

    to get properties from that exported object.

    You don’t need to learn anything new about modules here.

    The important thing is simply this:

    An object is a value.

    A function can receive an object.

    A function can return an object.

    A variable can refer to an object.

    A module can export an object.

    Once you understand objects, many things that previously looked unrelated start to look like the same idea.

    Scope and objects#

    We have spent some time thinking about scope.

    You know that a function gets its own names.

    For example:

    const x = 10;

function test() {
  const y = 20;

  console.log(x);
  console.log(y);
}

    The function can use x because x exists in the outer scope.

    And it can use y because y exists in its own scope.

    Objects don’t change the rules of scope.

    Consider:

    const person = {
  name: "Asha",
};

function test() {
  const person = {
    name: "Ravi",
  };

  console.log(person.name);
}

test();

console.log(person.name);

    Predict the output.

    There are two variables called person.

    They are in different scopes.

    The object inside the function is a different object from the object outside the function.

    This is another place where the distinction between variables and objects matters.

    A name belongs to a scope.

    A variable refers to a value.

    That value might be an object.

    The object itself is not “inside the scope” just because the variable referring to it is.

    A useful mental model#

    Let’s put the pieces together.

    Suppose we write:

    const person = {
  name: "Asha",
  age: 20,
};

    You can imagine a name table containing:

    person ───────────────► object

    and the object containing:

    ┌──────────────┐
│ name → Asha  │
│ age  → 20    │
└──────────────┘

    If we write:

    const another = person;

    we now have:

    person ──────────┐
                 ▼
             ┌──────────────┐
             │ name → Asha  │
             │ age  → 20    │
             └──────────────┘
                 ▲
another ─────────┘

    If we write:

    another.age = 21;

    we change the object.

    Both references now observe:

    age → 21

    But if we write:

    another = {
  name: "Ravi",
  age: 30,
};

    we change what another refers to.

    The original object is still there.

    This is the mental model you should practise.

    You do not need to imagine exactly how JavaScript’s memory is implemented inside the computer.

    The boxes and arrows are simply a useful way of reasoning about what your program is doing.

    When you are confused, draw them.

    Things to remember#

    Before you move on, make sure these ideas are clear.

    1. Objects group related values#

    const person = {
  name: "Asha",
  age: 20,
};

    2. Properties can be accessed with .#

    person.name;

    3. Properties can be accessed with []#

    person["name"];

    4. [] allows computed property access#

    const property = "name";

person[property];

    5. Objects can be changed#

    person.age = 21;

    6. const does not make an object immutable#

    const person = {
  age: 20,
};

person.age = 21; // works

    But:

    person = {}; // error

    7. Two variables can refer to the same object#

    const a = {
  x: 10,
};

const b = a;

    Changing the object through b is visible through a.

    8. Reassignment is different from mutation#

    b.x = 20;

    changes the object.

    b = {};

    changes what b refers to.

    9. Functions can receive objects#

    function show(point) {
  console.log(point.x);
}

    10. Functions can return objects#

    function makePoint() {
  return {
    x: 10,
    y: 20,
  };
}

    11. Be careful when modifying objects inside functions#

    As a general practice, avoid modifying objects passed into a function unless there is a good reason.

    Ask yourself:

    Is this function computing a new value, or is it changing something that someone else gave it?

    That question will become increasingly important as your programs grow.

    25. What happens?#

    This final one is a tracing exercise.

    Do not run it immediately.

    Read it carefully.

    let a = {
  value: 10,
};

let b = a;

function change(x) {
  x.value = 20;

  x = {
    value: 30,
  };

  x.value = 40;

  return x;
}

const c = change(b);

    Now predict all three:

    a.value;
b.value;
c.value;

    Then draw the objects and references at each stage:

    1. before change is called
    2. after x.value = 20
    3. after x = { value: 30 }
    4. after x.value = 40
    5. after the function returns

    Only then run the program.

    If your prediction was wrong, go back to the boxes and arrows.

    That is the point of the exercise.

    One last question#

    You have now seen objects used in two very different ways.

    We used an object to describe something:

    const person = {
  name: "Asha",
  age: 20,
};

    And we used an object as a lookup:

    const capitals = {
  India: "New Delhi",
  France: "Paris",
};

    What do these two uses have in common?

    In both cases, we have names associated with values.

    That is the basic idea behind JavaScript objects.

    There is a lot more to objects than this.

    But you now have the foundation you need to start using them deliberately.
