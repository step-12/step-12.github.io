    Functions

    September 19, 2026
    Javascript, Functions

    You have now started writing JavaScript programs in files.

    Until now, you have mostly been asking JavaScript questions in the REPL:

    > 10 % 2 === 0
true

> 17 % 2 === 0
false

    Now you can put those expressions into a program, save the program in a file, and run it.

    Today, we are going to look at a problem that appears very quickly when you start writing larger programs:

    What do you do when you find yourself writing the same computation again and again?

    The problem of repetition#

    Suppose you want to check whether three numbers are even.

    Open a new file called even.js.

    You could write:

    const number1 = 12;
const number2 = 17;
const number3 = 24;

if (number1 % 2 === 0) {
  console.log(true);
} else {
  console.log(false);
}

if (number2 % 2 === 0) {
  console.log(true);
} else {
  console.log(false);
}

if (number3 % 2 === 0) {
  console.log(true);
} else {
  console.log(false);
}

    Run the program.

    You should get:

    true
false
true

    Now look carefully at the three if statements.

    What changes between them?

    What stays the same?

    The numbers change:

    number1;
number2;
number3;

    But the actual computation does not change:

    number % 2 === 0;

    We have written the same idea three times.

    Imagine that instead of three numbers, you had thirty numbers.

    Would you want to write this thirty times?

    There is something interesting about this repetition.

    The computation:

    number % 2 === 0;

    is useful enough that we would like to give it a name.

    Then, instead of writing out the computation every time, perhaps we could say:

    “Do the even-number computation here.”

    JavaScript gives us a way to do exactly that.

    Give the computation a name#

    Replace the previous program with this:

    function isEven(number) {
  return number % 2 === 0;
}

    Read it carefully.

    We have given the computation a name:

    isEven;

    Now try calling it:

    console.log(isEven(12));
console.log(isEven(17));
console.log(isEven(24));

    Run the program.

    You should see:

    true
false
true

    Notice something important.

    We only wrote the computation once:

    number % 2 === 0;

    We can now use it as many times as we want.

    Try adding:

    console.log(isEven(0));
console.log(isEven(101));
console.log(isEven(200));

    Before running the program, predict the output.

    Then run it.

    What happened?#

    Look at this:

    isEven(12);

    You already know what this looks like.

    Earlier, you learned to write:

    console.log(12);

    That is a function call.

    Now you have written another function call:

    isEven(12);

    The 12 is the argument to the function.

    Look back at the function itself:

    function isEven(number) {
  return number % 2 === 0;
}

    There are several pieces here.

    function        isEven        (number)       { ... }
   │               │              │              │
   │               │              │              └── body
   │               │              └── parameter
   │               └── function name
   └── tells JavaScript we are defining a function

    The name number is a parameter.

    It is the name we use for the value supplied when the function is called.

    So when you write:

    isEven(12);

    you can think of the function as performing its computation with number representing 12.

    When you write:

    isEven(17);

    number represents 17 instead.

    Try this in the REPL:

    function isEven(number) {
  return number % 2 === 0;
}

    Then:

    isEven(12);

    and:

    isEven(13);

    Try several different numbers.

    You have now taken a computation and given it a name.

    That is already useful.

    But there is something more interesting happening here.

    What if we need more than one value?#

    So far, our function has taken one value:

    function isEven(number) {
  return number % 2 === 0;
}

    What if the computation needs two values?

    Let’s try a simple example.

    Suppose we want to add two numbers.

    We could write:

    function add(first, second) {
  return first + second;
}

    Now look at the function definition:

    function add(first, second) {

    There are two parameters:

    first
second

    When we call the function, we can give it two arguments:

    add(10, 20);

    What do you think this produces?

    Try it in the REPL.

    You should get:

    30

    The first argument goes to the first parameter:

    first  →  10

    and the second argument goes to the second parameter:

    second →  20

    So you can imagine the function’s table looking like this while it is running:

    NameValue
    first10
    second20

    The function then evaluates:

    first + second;

    which gives:

    30

    Try changing the arguments#

    Predict the result of each of these before running them:

    add(5, 7);
    add(100, 25);
    add(10, -3);

    The order matters.

    What do you think this produces?

    add(10, 20);

    What about:

    add(20, 10);

    For add, the answer happens to be the same.

    Let’s use a function where the order matters:

    function subtract(first, second) {
  return first - second;
}

    Predict:

    subtract(10, 3);

    and:

    subtract(3, 10);

    The first argument always corresponds to the first parameter.

    The second argument always corresponds to the second parameter.

    So when you see:

    subtract(10, 3);

    you can think:

    first  →  10
second →  3

    and therefore:

    first - second;

    becomes:

    10 - 3;

    Functions are not limited to one input.

    You can give a function as many parameters as the computation needs:

    function someFunction(first, second, third) {
  // ...
}

    and then provide the corresponding arguments when you call it:

    someFunction(10, 20, 30);

    For now, pay attention to the correspondence:

    parameters are the names in the function definition; arguments are the values supplied when the function is called.

    What does isEven(12) produce?#

    Try this in the REPL:

    const result = isEven(12);

    Now:

    result;

    What do you expect?

    You should get:

    true

    This tells us something important.

    The function call:

    isEven(12);

    is itself an expression.

    It produces a value.

    That means we can use it anywhere we could use that value.

    For example:

    const result = isEven(12);

console.log(result);

    Or:

    console.log(isEven(12));

    Or:

    if (isEven(12)) {
  console.log("12 is even");
}

    In all three cases, the function is being called and the value it produces is being used.

    Let’s change the function#

    Look at this:

    function isEven(number) {
  return number % 2 === 0;
}

    What do you think return does?

    Don’t look it up.

    Instead, experiment.

    Change the function to:

    function isEven(number) {
  number % 2 === 0;
}

    Now try:

    isEven(12);

    What happened?

    Try:

    const result = isEven(12);
result;

    What value did you get?

    You should find that the result is:

    undefined

    Now put return back:

    function isEven(number) {
  return number % 2 === 0;
}

    And try again:

    isEven(12);

    This time:

    true

    The return allows the function to produce the value of the expression after it:

    return number % 2 === 0;

    So:

    isEven(12);

    produces:

    true;

    and:

    isEven(13);

    produces:

    false;

    This is why we can write:

    const result = isEven(12);

    The value produced by the function call becomes the value stored in result.

    Computing and displaying are different things#

    There is another problem in our original program.

    We have solved one kind of repetition.

    Instead of repeatedly writing:

    number % 2 === 0;

    we can write:

    isEven(number);

    But suppose we want the program to say:

    12 is even
17 is odd
24 is even

    We might write:

    const number1 = 12;
const number2 = 17;
const number3 = 24;

console.log(number1 + " is even");
console.log(number2 + " is odd");
console.log(number3 + " is even");

    There is repetition here too.

    More importantly, there are now two different jobs happening:

    1. deciding whether a number is even;
    2. displaying something to the user.

    Let’s separate them.

    First, keep our computation:

    function isEven(number) {
  return number % 2 === 0;
}

    Now write another function:

    function describeEven(number) {
  const description = isEven(number) ? "even" : "odd";

  return `${number} is ${description}`;
}

    Now try:

    console.log(describeEven(12));
console.log(describeEven(17));
console.log(describeEven(24));

    What does describeEven produce?

    It produces a string.

    Try:

    const message = describeEven(12);

    Then:

    console.log(message);

    The function computes a value.

    The console.log displays that value.

    This distinction will become increasingly useful as your programs get larger.

    Ask yourself:

    Is this function figuring something out, or is it displaying something?

    For example:

    isEven(12);

    figures something out.

    console.log(isEven(12));

    displays the result.

    And remember something from the previous lesson:

    console.log("hello");

    does display something, but the function call itself produces:

    undefined

    So console.log is useful for its side effect—printing something—not because it gives you a useful value to continue computing with.

    Where do the variables live?#

    You have already worked with lookup tables when drawing expression trees.

    For example, if you have:

    const x = 10;
const y = 20;

console.log(x + y);

    you can imagine a table like this:

    NameValue
    x10
    y20

    When JavaScript evaluates:

    x + y;

    it looks up x and y in the table.

    You have already practised doing exactly this with expression trees: look up the names, then evaluate the expression.

    Now let’s see what happens when we put variables inside a block.

    Try an experiment#

    Open the REPL and enter:

    if (true) {
  const x = 10;

  console.log(x);
}

    This prints:

    10

    So x clearly exists when JavaScript evaluates:

    console.log(x);

    Now try:

    console.log(x);

    What happens?

    You should get an error.

    But why?

    We can understand this using the same lookup-table idea.

    When JavaScript is inside the if block, imagine that it has another table:

    Outside the block:

    NameValue

    Inside the block:

    NameValue
    x10

    When JavaScript evaluates:

    console.log(x);

    inside the block, it can find x in the current table.

    When you evaluate:

    console.log(x);

    outside the block, that table is no longer the current table.

    There is no x there.

    This is what scope means.

    A scope is a region of your program with its own set of names.

    You can think of it as JavaScript using a different lookup table.

    What about variables outside the block?#

    Try this:

    const x = 10;

if (true) {
  const y = 20;

  console.log(x);
  console.log(y);
}

    Both values can be printed.

    Why?

    Think about the tables again.

    The outer table contains:

    NameValue
    x10

    The if block has another table:

    NameValue
    y20

    When JavaScript is inside the block and looks for y, it finds it in the current table.

    What happens when it looks for x?

    There is no x in the block’s table.

    So it looks in the outer table.

    It finds:

    x → 10

    This is why this works:

    console.log(x);

    inside the block.

    But if we leave the block and try:

    console.log(y);

    JavaScript cannot find y in the outer table.

    The table belonging to the if block is no longer the current table.

    Try changing the table#

    Try this:

    const x = 10;

if (true) {
  const x = 20;

  console.log(x);
}

console.log(x);

    Before you run it, predict the output.

    You might expect JavaScript to complain:

    “You already have a variable called x!”

    But it doesn’t.

    The output is:

    20
10

    Why?

    There are two different tables.

    The outer table contains:

    NameValue
    x10

    The table for the if block contains:

    NameValue
    x20

    When JavaScript is inside the block, it finds x in the current table:

    x → 20

    When it leaves the block, the current table is the outer one:

    x → 10

    So the same name can have different values in different scopes.

    The important thing is not that JavaScript has two variables fighting over the same name.

    They are in different tables.

    Functions have their own table#

    Now we can apply exactly the same idea to functions.

    Try:

    function test() {
  const number = 12;

  console.log(number);
}

test();

    This works.

    Now try:

    console.log(number);

    What happens?

    Again, think about the tables.

    Outside the function, we might have:

    NameValue

    When test() runs, the function has its own table:

    NameValue
    number12

    Inside the function, JavaScript can look up:

    number;

    in that table.

    Outside the function, that is not the current table anymore.

    So number cannot be found.

    This is the same idea you just saw with an if block.

    A function creates another scope.

    Parameters go into the table too#

    Look at our isEven function:

    function isEven(number) {
  return number % 2 === 0;
}

    When we call:

    isEven(12);

    you can think of the function getting its own table:

    NameValue
    number12

    Then JavaScript evaluates:

    number % 2 === 0;

    using that table.

    If we call:

    isEven(17);

    the function gets a function scope in which:

    NameValue
    number17

    The name is the same.

    The value is different.

    The function’s parameter is simply another name that exists in its scope.

    This gives you a useful way to think about functions:

    When a function runs, it gets its own lookup table.

    Variables declared inside the function go into that table.

    Its parameters go into that table.

    When JavaScript evaluates an expression inside the function, it looks for names in the appropriate table.

    You don’t need to think about the memory inside the computer or how JavaScript implements this.

    For now, keep using the lookup-table model you already know.

    A scope is, in effect, a different table of names and values.

    Building on functions#

    Now that we have isEven, consider another question.

    How could we write isOdd?

    You could calculate oddness from scratch:

    function isOdd(number) {
  return number % 2 !== 0;
}

    That works.

    But there is another possibility.

    Think about what we already know:

    • if a number is even, it is not odd;
    • if a number is not even, it is odd.

    So try:

    function isOdd(number) {
  return !isEven(number);
}

    Test it:

    console.log(isOdd(3));
console.log(isOdd(4));
console.log(isOdd(17));
console.log(isOdd(20));

    Predict the output before running it.

    Notice what happened.

    isOdd uses isEven.

    A function can call another function.

    This is one of the reasons giving computations names is useful.

    Once you have written a useful computation, you don’t have to write it again.

    Other parts of your program can build on it.

    A bigger problem: classifying numbers#

    Let’s try something slightly larger.

    Suppose we have two numbers:

    const number1 = 15;
const number2 = -3;

    We want the program to tell us whether each number is:

    • zero
    • positive
    • negative

    We could start like this:

    if (number1 === 0) {
  console.log("zero");
} else if (number1 > 0) {
  console.log("positive");
} else {
  console.log("negative");
}

if (number2 === 0) {
  console.log("zero");
} else if (number2 > 0) {
  console.log("positive");
} else {
  console.log("negative");
}

    Run it.

    You should get:

    positive
negative

    But once again, look at the program.

    We have written the same decision twice.

    What changes?

    Only the number.

    The classification itself is the same.

    So let’s give that computation a name.

    How might we write:

    classify(number);

    so that it produces:

    "zero"

    or:

    "positive"

    or:

    "negative"

    Try writing it yourself before looking at the solution.

    Remember that a function can return a value.

    One possible solution is:

    function classify(number) {
  if (number === 0) {
    return "zero";
  }

  if (number > 0) {
    return "positive";
  }

  return "negative";
}

    Now we can write:

    console.log(classify(15));
console.log(classify(-3));
console.log(classify(0));

    The result is:

    positive
negative
zero

    Look carefully at the structure.

    function classify(number) {
  if (number === 0) {
    return "zero";
  }

  if (number > 0) {
    return "positive";
  }

  return "negative";
}

    The first return does something important.

    When:

    number === 0;

    is true, the function returns:

    "zero";

    and the function is finished.

    It does not continue to the next if.

    If the number is not zero, we reach the next if.

    If:

    number > 0;

    is true, we return:

    "positive";

    Otherwise, we reach the final line:

    return "negative";

    This is a useful pattern.

    Instead of making one large if/else if/else, you can sometimes ask a question and immediately return when you know the answer:

    if (...) {
  return "...";
}

if (...) {
  return "...";
}

return "...";

    You will see this pattern often.

    Keep the computation separate#

    Now imagine that we want to classify two numbers:

    const number1 = 15;
const number2 = -3;

    We can write:

    console.log(classify(number1));
console.log(classify(number2));

    Notice where console.log is.

    It is outside classify.

    classify does not print anything.

    It computes a classification and returns it.

    The program decides what to do with that value.

    For example:

    const result = classify(15);

console.log(result);

    Or:

    if (classify(15) === "positive") {
  console.log("The number is positive.");
}

    The function gives us a value.

    The rest of the program decides what to do with that value.

    What happens first?#

    There is one more thing you need to understand.

    Consider this program:

    function greet() {
  console.log("hello");
}

console.log("start");

greet();

console.log("end");

    Before running it, predict the exact output.

    Write down what you think will happen.

    Then run it.

    You should get:

    start
hello
end

    Now let’s make it slightly more interesting:

    function first() {
  console.log("first");
}

function second() {
  console.log("second");
  first();
}

console.log("start");

second();

console.log("end");

    Again, predict the output.

    Don’t run it yet.

    Follow the program from top to bottom.

    The output is:

    start
second
first
end

    Why?

    The function declarations themselves don’t print anything.

    The program reaches:

    console.log("start");

    so it prints:

    start

    Then:

    second();

    calls second.

    Inside second:

    console.log("second");

    prints:

    second

    Then:

    first();

    calls first, which prints:

    first

    Eventually second finishes, and the program continues:

    console.log("end");

    So:

    start
second
first
end

    One strange thing#

    There is something interesting about function declarations.

    Try this:

    greet();

function greet() {
  console.log("hello");
}

    What do you expect?

    Run it.

    It works.

    The function is declared after the call, but JavaScript still allows this form of function declaration to be called.

    You don’t need to worry about how JavaScript makes this possible.

    For now, there is a more useful convention:

    Write your function declarations before the code that uses them.

    So prefer:

    function greet() {
  console.log("hello");
}

greet();

    rather than:

    greet();

function greet() {
  console.log("hello");
}

    It makes the program easier to read.

    You will encounter another way of creating functions later. For now, stick to the function syntax you have learned today.

    Exercises#

    For each exercise, create a separate JavaScript file.

    Don’t put all the exercises into one file.

    For every exercise, first try to predict what your program will do. Then run it and compare the result with your prediction.

    1. isPositive#

    Write a function:

    isPositive(number);

    that returns true when the number is greater than zero and false otherwise.

    Test it with several numbers.

    Try:

    10
-10
0
1
-1

    2. isZero#

    Write:

    isZero(number);

    It should return true when the number is zero and false otherwise.

    Test it with at least five numbers.

    3. isOdd#

    Write:

    isOdd(number);

    Do not repeat the divisibility calculation from isEven.

    Use the function you already wrote.

    For example:

    function isOdd(number) {
  // ...
}

    Test your function.

    4. absolute#

    Write a function:

    absolute(number);

    It should return the positive version of a number.

    For example:

    absolute(10)   → 10
absolute(-10)  → 10
absolute(0)    → 0

    Think about the different cases before writing the function.

    5. describeNumber#

    Write:

    describeNumber(number);

    It should return one of:

    "zero"
"positive"
"negative"

    Do not print from inside the function.

    Test it like this:

    console.log(describeNumber(10));
console.log(describeNumber(-10));
console.log(describeNumber(0));

    6. Use a function inside another function#

    Write:

    isNonZero(number);

    It should return true when a number is not zero.

    Use your isZero function.

    Do not repeat the comparison with zero inside isNonZero.

    7. String length#

    You already know that strings have a .length.

    Write:

    isLong(word);

    It should return true when the string contains more than 5 characters.

    For example:

    isLong("hello")      → false
isLong("elephant")   → true

    You only need .length. You do not need any new string methods.

    8. Describe a word#

    Write:

    describeWord(word);

    It should return:

    "empty"

    when the string has length 0, and:

    "non-empty"

    otherwise.

    Test it with several strings.

    9. Predict the output#

    Do not run this program yet.

    Write down the exact order in which the words will be printed.

    function first() {
  console.log("A");
}

function second() {
  console.log("B");
  first();
  console.log("C");
}

console.log("D");
second();
console.log("E");

    What is the output?

    Only after you have written down your answer should you run the program.

    Were you correct?

    10. Trace the program#

    Again, do not run the program immediately.

    function isEven(number) {
  return number % 2 === 0;
}

function describe(number) {
  if (isEven(number)) {
    return "even";
  }

  return "odd";
}

console.log("start");
console.log(describe(7));
console.log(describe(12));
console.log("end");

    Predict the exact output.

    Then run it.

    Now explain, in your own words, the order in which the function calls happen.

    You have now seen something fundamental about programming:

    A useful computation does not have to remain an unnamed piece of code.

    You can give it a name:

    function isEven(number) {
  return number % 2 === 0;
}

    and then use that computation elsewhere:

    isEven(10);

    A function can receive a value, perform a computation, and return a value.

    Other functions can use that value.

    And your program can decide what to do with it.

    That gives you a way to take a repeated piece of thinking, give it a name, and build new pieces of thinking on top of it.
