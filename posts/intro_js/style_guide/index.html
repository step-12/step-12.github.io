      Javascript, Style

      JavaScript Style Guide#

      Writing code is not only about making a computer do something. It is also about writing code that another person can read, understand, and change.

      This guide describes the conventions we will use when writing JavaScript.

      These are not arbitrary rules. Most of them exist because they make code easier to read and reason about.

      When you work on an assignment, follow these conventions unless the assignment says otherwise.

      Formatting#

      Formatting should be predictable.

      We use the default JavaScript/TypeScript formatter provided by VS Code. Do not spend time manually adjusting whitespace that the formatter can handle for you.

      Line length#

      Keep lines to 80 characters or fewer whenever practical.

      Long lines are difficult to read, particularly when several pieces of code are being compared side by side.

      VS Code can show you where 80 characters are:

      {
  "editor.rulers": [80]
}

      The ruler is a guide, not a hard error. If keeping a line under 80 characters makes the code substantially harder to understand, use your judgment.

      Indentation#

      Use 2 spaces for indentation.

      Do not use tabs.

      A VS Code project can enforce this with:

      {
  "editor.tabSize": 2,
  "editor.insertSpaces": true,
  "editor.detectIndentation": false
}

      For example:

      function drawRectangle(x, y, width, height) {
  if (width > 0) {
    drawRectangleOutline(x, y, width, height);
  }
}

      The indentation should make the structure of the program immediately visible.

      Blank lines#

      Use blank lines to separate different pieces of thought.

      For example:

      const width = 800;
const height = 600;

function drawBackground() {
  // ...
}

function drawPlayer() {
  // ...
}

function main() {
  // ...
}

      A file should not look like one large block of text.

      Naming#

      Names are one of the most important parts of readable code.

      A good name tells the reader what something represents without requiring them to inspect how it is used.

      Variables are usually nouns#

      Variables represent things, so their names should generally describe those things.

      Good:

      const width = 200;
const height = 100;
const distance = 50;
const playerPosition = { x: 100, y: 200 };

      Less useful:

      const thing = 200;
const value = 100;
const data = 50;

      value and data are not inherently bad names, but they often mean that we have not thought carefully enough about what the value represents.

      Prefer the more specific name when one is available.

      Functions are usually verbs#

      Functions do something.

      Good:

      drawCircle();
calculateDistance();
findClosestPoint();
moveScanner();

      A function named calculateDistance tells us that it performs an operation.

      Compare that with:

      distance();

      The latter does not tell us whether the function calculates, retrieves, changes, or displays a distance.

      Prefer names that describe the action performed by the function.

      Predicates should sound like questions#

      A predicate is a function whose answer is true or false.

      Name predicates so that they read naturally as questions.

      Good:

      isVisible();
isInside();
hasCollided();
canMove();
shouldDraw();

      This makes code easier to read:

      if (isVisible(point)) {
  drawPoint(point);
}

      The condition reads almost like English:

      If the point is visible, draw the point.

      Avoid vague names such as:

      checkPoint();
checkCollision();

      if the function actually returns a boolean.

      Prefer:

      isInside();
hasCollided();

      Use camelCase#

      Variables and functions use camelCase.

      const screenWidth = 800;

function calculateDistance() {
  // ...
}

      Do not use snake_case:

      const screen_width = 800;

      Do not use PascalCase for ordinary variables or functions:

      const ScreenWidth = 800;

function CalculateDistance() {
  // ...
}

      We will encounter PascalCase later for things such as classes and constructors. For the JavaScript we are writing now, use camelCase.

      Variables#

      Prefer const#

      If a variable does not need to change, use const.

      const width = 800;
const height = 600;

      Use let when the value needs to change:

      let x = 0;

x = x + 1;

      Do not use let simply because you might change the value someday.

      Choose const when the value is not going to be reassigned.

      Declare variables together#

      Avoid declaring variables randomly throughout a function.

      Prefer:

      function draw() {
  const x = 100;
  const y = 50;
  const width = 200;
  const height = 100;

  drawRectangle(x, y, width, height);
}

      rather than:

      function draw() {
  const x = 100;

  drawSomething(x);

  const y = 50;

  doSomethingElse(y);

  const width = 200;
  const height = 100;

  drawRectangle(x, y, width, height);
}

      Declarations should generally appear near the beginning of a block, followed by the code that uses them.

      This makes it easier to see what information a function needs before reading what it does.

      There are exceptions. A variable that exists only for a small, local piece of logic can be declared close to where it is used.

      The goal is not to obey a mechanical rule. The goal is to make the structure of the code easy to see.

      Avoid global variables#

      Avoid mutable global variables whenever possible.

      Consider:

      let x = 100;

function move() {
  x = x + 1;
}

function reset() {
  x = 0;
}

      There is no obvious answer to the question:

      Where can x change?

      It can change anywhere in the program.

      As programs become larger, this becomes increasingly difficult to reason about.

      Compare this with:

      function move(x) {
  return x + 1;
}

function reset() {
  return 0;
}

      Now the value is passed into the function and returned from it. We can understand what the function does by looking at the function itself.

      A useful rule is:

      Keep data close to the code that owns it.

      Global constants such as configuration values are often fine:

      const WIDTH = 800;
const HEIGHT = 600;

      The problem is not the existence of something at the top level. The problem is uncontrolled mutable state that can be changed from anywhere.

      Functions#

      Functions should make code easier to understand.

      Give functions one clear responsibility#

      A function should have one coherent job.

      For example:

      function drawPlayer() {
  drawPlayerBody();
  drawPlayerHead();
}

      This is still one responsibility: drawing the player.

      But this function is doing several unrelated things:

      function updateEverything() {
  calculateDistance();
  checkCollision();
  updateScore();
  drawPlayer();
  drawScore();
}

      It would be better to separate the different responsibilities:

      function update() {
  calculateDistance();
  checkCollision();
  updateScore();
}

function draw() {
  drawPlayer();
  drawScore();
}

      Do not interpret “one responsibility” to mean that every function should contain only one statement.

      The question to ask is:

      Can I describe what this function does in one clear sentence?

      Prefer returning values#

      A function is often easier to understand when it takes inputs and produces an output.

      For example:

      function calculateDistance(a, b) {
  // ...
  return distance;
}

const distance = calculateDistance(pointA, pointB);

      The result is explicit.

      Prefer this over functions that secretly modify unrelated variables somewhere else in the program.

      Do not modify function arguments#

      Prefer not to change the values passed into a function.

      For example, avoid:

      function move(point) {
  point.x = point.x + 1;
  point.y = point.y + 1;
}

      Prefer:

      function move(point) {
  return {
    x: point.x + 1,
    y: point.y + 1
  };
}

      Now the function receives a point and produces a new point.

      This makes the behavior easier to reason about.

      There are situations where modifying an argument can be useful, particularly with certain data structures. For now, however, make not modifying arguments your default.

      Control Flow#

      Control flow should make the possible paths through a program easy to follow.

      Prefer early returns#

      Consider:

      function drawPoint(point) {
  if (isVisible(point)) {
    draw(point);
  }
}

      There is nothing particularly wrong with this.

      But when there is more code after the condition, nesting can quickly become difficult to read.

      Prefer:

      function drawPoint(point) {
  if (!isVisible(point)) {
    return;
  }

  draw(point);
}

      The function now says:

      If the point is not visible, stop. Otherwise, draw it.

      This pattern is called an early return.

      Early returns are especially useful for handling conditions that prevent the rest of a function from doing its work.

      Avoid unnecessary else#

      If one branch returns from a function, there is usually no need for an else.

      Instead of:

      function getSign(number) {
  if (number < 0) {
    return "negative";
  } else {
    return "positive";
  }
}

      write:

      function getSign(number) {
  if (number < 0) {
    return "negative";
  }

  return "positive";
}

      The second version is easier to read because the two paths are simply:

      1. If the number is negative, return "negative".
      2. Otherwise, return "positive".

      There is no need to explicitly write “otherwise”.

      Avoid unnecessary else if#

      Early returns can also simplify chains of conditions.

      For example:

      function getGrade(score) {
  if (score >= 90) {
    return "A";
  }

  if (score >= 80) {
    return "B";
  }

  if (score >= 70) {
    return "C";
  }

  return "D";
}

      Each condition is handled independently.

      However, do not twist perfectly readable code merely to eliminate every else if.

      This is also reasonable:

      if (score >= 90) {
  return "A";
} else if (score >= 80) {
  return "B";
} else if (score >= 70) {
  return "C";
}

      The goal is readable control flow, not following a rule for its own sake.

      Ternary Expressions#

      The ternary operator is useful, but it is very easy to use badly.

      A ternary chooses between two values:

      const color = isActive ? "red" : "white";

      This is good use of a ternary.

      So is:

      return distance < 10 ? "near" : "far";

      A useful rule is:

      Use a ternary when you are choosing a value. Use if when you are choosing an action.

      Avoid using a ternary merely to perform one of two actions:

      isActive ? drawRed() : drawWhite();

      Write:

      if (isActive) {
  drawRed();
} else {
  drawWhite();
}

      It is much clearer.

      Do not write deeply nested ternaries:

      const result = a
  ? b
  : c
    ? d
    : e;

      If you need to stop and decode the expression, use if.

      Organizing a File#

      A file should have a predictable structure.

      For the programs we are writing, use this general order:

      1. require statements
      2. Constants and configuration
      3. Function declarations
      4. The main entry point

      For example:

      const r = require("raylib");

const WIDTH = 800;
const HEIGHT = 600;
const FPS = 60;

function setup() {
  r.InitWindow(WIDTH, HEIGHT, "Example");
  r.SetTargetFPS(FPS);
}

function update() {
  // ...
}

function draw() {
  // ...
}

function main() {
  setup();

  while (!r.WindowShouldClose()) {
    update();
    draw();
  }

  r.CloseWindow();
}

main();

      This is a sensible default.

      A reader opening the file immediately knows where to look for:

      • dependencies,
      • configuration,
      • functions,
      • and program execution.

      Keep main near the bottom#

      The program should generally read from its ingredients toward its execution.

      For example:

      const r = require("raylib");

const WIDTH = 800;
const HEIGHT = 600;

function setup() {
  // ...
}

function update() {
  // ...
}

function draw() {
  // ...
}

function main() {
  // ...
}

main();

      Someone reading the file from top to bottom encounters the things needed to understand the program before seeing the program actually run.

      Magic Numbers#

      A magic number is a number whose meaning is unclear from the code.

      For example:

      r.DrawRectangle(100, 50, 200, 100, r.WHITE);

      What do those numbers mean?

      Compare:

      const x = 100;
const y = 50;
const width = 200;
const height = 100;

r.DrawRectangle(x, y, width, height, r.WHITE);

      Now the meaning is obvious.

      The goal is not to replace every number with a constant.

      This is perfectly readable:

      x = x + 1;

      There is nothing mysterious about 1.

      But if you write:

      if (distance < 37) {
  // ...
}

      you should ask:

      What is special about 37?

      If the number has a meaningful role, give that meaning a name:

      const TARGET_DISTANCE = 37;

if (distance < TARGET_DISTANCE) {
  // ...
}

      Comments#

      Comments should explain things that the code cannot easily explain by itself.

      Avoid comments that merely repeat the code:

      // Add one to x.
x = x + 1;

      The code already says that.

      A useful comment explains why:

      // The scanner moves one pixel per frame.
x = x + 1;

      Even better, when possible, make the code itself communicate the reason.

      Compare:

      x = x + 1;

      with:

      const SCANNER_SPEED = 1;

x = x + SCANNER_SPEED;

      The second version may make the comment unnecessary.

      A good principle is:

      Prefer clear code over comments that explain unclear code.

      Comments are useful when they capture an important idea, assumption, limitation, or reason that cannot be expressed naturally in the code.

      Avoid Unnecessary Abbreviations#

      Names should be short enough to read, but long enough to understand.

      Prefer:

      const width = 200;
const height = 100;
const point = getPoint();

      over:

      const w = 200;
const h = 100;
const p = getPoint();

      There are exceptions.

      Names such as x and y are perfectly reasonable when representing coordinates:

      const x = 100;
const y = 50;

      The important question is:

      Would a reader understand this name without having to look elsewhere?

      Use your judgment.

      Boolean Expressions#

      When a value is already a boolean, do not compare it unnecessarily with true or false.

      Prefer:

      if (isVisible) {
  draw();
}

      over:

      if (isVisible === true) {
  draw();
}

      Similarly, prefer:

      if (!isVisible) {
  return;
}

      over:

      if (isVisible === false) {
  return;
}

      Good predicate names make this especially readable:

      if (isInside(point, rectangle)) {
  draw(point);
}

      A Note About Rules#

      These conventions are here to help us write readable programs.

      They are not laws of programming.

      There will be situations where two rules appear to conflict.

      For example, we prefer short functions, but splitting a simple function into five tiny functions can make a program harder to understand.

      We prefer avoiding else if, but sometimes a short sequence of else if statements is the clearest way to express an idea.

      We prefer avoiding magic numbers, but turning every 1 and 2 into a named constant would make code worse.

      The purpose of a style guide is not to make code conform to a collection of rules.

      The purpose is to make code easier for people to read.

      When in doubt, ask:

      Does this make the code easier or harder to understand?

      That is the principle behind everything in this guide.
