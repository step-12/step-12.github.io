    More about functions

    September 19, 2026

    Function calls inside function calls#

    So far, you have seen function calls like this:

    double(5)

    When you see this, you know that double(5) is an expression. The function runs, and eventually the expression produces a value.

    Let’s make the expression a little more interesting.

    Suppose we have:

    function double(number) {
  return number * 2;
}

function addOne(number) {
  return number + 1;
}

    Now consider:

    addOne(double(5))

    Don’t run it yet.

    What value should addOne receive?

    Think about what has to happen first.

    addOne needs an argument. In this case, its argument is:

    double(5)

    So JavaScript first needs to find out what double(5) produces.

    double(5)
   ↓
  10
   ↓
addOne(10)
   ↓
  11

    So:

    addOne(double(5))

    produces:

    11

    Try it in the REPL.

    Now try this:

    double(addOne(5))

    Is the answer still 11?

    No.

    This time:

    addOne(5)
   ↓
  6
   ↓
double(6)
   ↓
  12

    The order in which the functions are written matters.

    Look inside first#

    You have already learned to think about expressions as trees.

    Consider:

    addOne(double(5))

    There is an outer function call:

           addOne
          |
       double
          |
          5

    The addOne call cannot be completed until its argument is known.

    That means the inner expression:

    double(5)

    has to be evaluated first.

    Then its result becomes the argument to addOne.

    Let’s make the expression slightly bigger:

    function add(a, b) {
  return a + b;
}

    Now:

    add(double(5), addOne(5))

    There are two function calls inside the arguments to add.

    What does add eventually receive?

    Work it out before running it.

    double(5)   → 10

addOne(5)   → 6

add(10, 6)  → 16

    So the whole expression produces:

    16

    Notice something important.

    add could not finish until both of its arguments had been evaluated.

    You can think of the expression tree like this:

              add
         /   \
    double   addOne
       |       |
       5       5

    The smaller expressions have to produce their values before the larger expression can be completed.

    Try these in the REPL:

    add(double(3), addOne(7))

    and:

    addOne(double(addOne(3)))

    Don’t just calculate the final answer.

    Ask yourself:

    Which function call has to happen first?

    Then:

    What value does it produce?

    Then:

    Where does that value go?

    This is going to become increasingly important.

    What is executing right now?#

    Consider this:

    function double(number) {
  return number * 2;
}

function addOne(number) {
  return number + 1;
}

console.log(addOne(double(5)));

    Let’s slow this down.

    The first thing that needs to happen is:

    double(5)

    While double is running, has addOne run yet?

    No.

    addOne is waiting.

    In fact, the whole expression is waiting for double(5) to produce a value.

    You can imagine the situation like this:

    addOne(double(5))
        ↑
     waiting

    Then double(5) finishes:

    double(5) → 10

    Now the expression has effectively become:

    addOne(10)

    So addOne can run:

    addOne(10) → 11

    And finally:

    console.log(11)

    runs.

    There is a useful way to describe this:

    A function call can be waiting for another function call to finish.

    Let’s make this visible.

    While double(5) is running, imagine that we have:

    addOne(double(5))

    and we are currently inside:

    double(5)

    When double returns 10, we go back to where we were waiting.

    Then we continue with:

    addOne(10)

    This happens every time one function calls another.

    But there is a problem.

    What if the calls become deeper?

    Consider:

    f(g(h(x)))

    What is running?

    What is waiting?

    And where do we go when a function returns?

    We need a better model.

    The call stack#

    Let’s look at a small example again:

    function double(number) {
  return number * 2;
}

function addOne(number) {
  return number + 1;
}

console.log(addOne(double(5)));

    We know that double(5) happens first.

    Imagine that JavaScript keeps track of the calls that are currently active.

    When double(5) begins, we can imagine this:

    double(5)

    Then double returns.

    It is finished, so it disappears:

    Now addOne(10) begins:

    addOne(10)

    Then that finishes too.

    This collection of currently active calls is called the call stack.

    The word stack is useful here because calls are added and removed in a particular order.

    A new call goes on top.

    When a call finishes, the call on top is removed.

    Let’s look at a slightly deeper example.

    function a(number) {
  return b(number);
}

function b(number) {
  return c(number);
}

function c(number) {
  return number + 1;
}

console.log(a(5));

    Don’t run it yet.

    What happens when we call:

    a(5)

    a begins running.

    a(5)

    Then a calls b(5).

    Now both calls are active:

    b(5)
a(5)

    b is on top because it is the function currently executing.

    Then b calls c(5):

    c(5)
b(5)
a(5)

    Now c returns:

    c(5) → 6

    So c disappears:

    b(5)
a(5)

    b can now continue. It receives the value 6 from c.

    Then b returns:

    b(5) → 6

    Now:

    a(5)

    is all that remains.

    Finally, a returns:

    a(5) → 6

    And the call stack is empty again.

    The important thing to notice is that calls don’t all run at once.

    At any particular moment, there is a function call that is currently executing, while other calls are waiting underneath it.

    You can draw the stack yourself when tracing a program.

    For example:

    function f(number) {
  return g(number + 1);
}

function g(number) {
  return h(number * 2);
}

function h(number) {
  return number - 3;
}

console.log(f(4));

    Before you run it, draw the call stack as it changes.

    Ask yourself:

    Which function is executing at this point?

    What is waiting for it?

    What happens when it returns?

    This is exactly where your expression-tree model and the call-stack model work together.

    The expression tree helps you see what needs to be evaluated.

    The call stack helps you see which calls are currently active and which calls are waiting.

    When a function calls itself#

    There is one more kind of function call we need to understand.

    You already know this idea from mathematics.

    For example:

    factorial(5) = 5 × factorial(4)

factorial(4) = 4 × factorial(3)

factorial(3) = 3 × factorial(2)

factorial(2) = 2 × factorial(1)

factorial(1) = 1

    You have already seen that a mathematical definition can describe a problem in terms of a smaller version of the same problem.

    We can write the same idea in JavaScript:

    function factorial(number) {
  if (number === 1) {
    return 1;
  }

  return number * factorial(number - 1);
}

    Look carefully at this line:

    return number * factorial(number - 1);

    What happens when we call:

    factorial(5)

    Don’t run it yet.

    The function reaches:

    factorial(5 - 1)

    which is:

    factorial(4)

    So now another call to factorial begins.

    The call stack looks like:

    factorial(4)
factorial(5)

    Then factorial(4) calls:

    factorial(3)

    So:

    factorial(3)
factorial(4)
factorial(5)

    Then:

    factorial(2)
factorial(3)
factorial(4)
factorial(5)

    Then:

    factorial(1)
factorial(2)
factorial(3)
factorial(4)
factorial(5)

    Now something different happens.

    factorial(1) reaches:

    if (number === 1) {
  return 1;
}

    It returns.

    So factorial(1) disappears from the stack.

    But factorial(2) has not finished.

    It was waiting for the result of:

    factorial(1)

    Now that result is available:

    factorial(1) → 1

    So factorial(2) can finish:

    2 × 1 → 2

    Then:

    factorial(3) → 3 × 2 → 6

    Then:

    factorial(4) → 4 × 6 → 24

    And finally:

    factorial(5) → 5 × 24 → 120

    The calls grew downwards:

    factorial(5)
factorial(4)
factorial(3)
factorial(2)
factorial(1)

    Then they returned upwards:

    factorial(1) → 1
factorial(2) → 2
factorial(3) → 6
factorial(4) → 24
factorial(5) → 120

    There is nothing special about the call stack here.

    This is important.

    Recursion does not create a new kind of function call.

    It is still just a function call.

    The only unusual thing is that the function calls itself.

    A smaller recursive example#

    Let’s look at one where the output is easier to see.

    function countdown(number) {
  if (number === 0) {
    return;
  }

  console.log(number);
  countdown(number - 1);
}

    What will this print?

    Don’t run it.

    Predict:

    countdown(3);

    You should be able to trace:

    countdown(3)
countdown(2)
countdown(1)
countdown(0)

    But notice when the console.log happens.

    countdown(3) prints 3 before making the next call.

    Then countdown(2) prints 2.

    Then countdown(1) prints 1.

    So the output is:

    3
2
1

    Now look at the function again.

    There is no value being built up and returned here. The observable result comes from:

    console.log(number);

    That is different from our factorial example, where the important result was the value returned by the function.

    Let’s write another recursive function:

    function sumTo(number) {
  if (number === 0) {
    return 0;
  }

  return number + sumTo(number - 1);
}

    What does this produce?

    sumTo(4)

    Trace the calls:

    sumTo(4)
sumTo(3)
sumTo(2)
sumTo(1)
sumTo(0)

    Now trace the returns:

    sumTo(0) → 0
sumTo(1) → 1 + 0 → 1
sumTo(2) → 2 + 1 → 3
sumTo(3) → 3 + 3 → 6
sumTo(4) → 4 + 6 → 10

    Notice how closely this resembles the factorial example.

    The function keeps asking for the answer to a smaller problem.

    Eventually it reaches the smallest problem it knows how to answer directly.

    That is why the condition:

    if (number === 0)

    is so important.

    Without it, the calls would keep going.

    One more thing about recursion#

    You might reasonably ask:

    Why not just write five lines and calculate the answer?

    For example, why not calculate:

    4 + 3 + 2 + 1

    directly?

    Sometimes you should.

    Recursion is not something you should use merely because you can.

    It becomes useful when a problem naturally has this shape:

    To solve this problem, solve a smaller version of the same problem.

    Mathematical recursion is a good example because the definition itself has that structure.

    You already know this way of thinking from mathematics. JavaScript is simply giving you a way to execute those definitions.

    Trace before you run#

    Let’s finish with something more difficult.

    Consider:

    function f(number) {
  if (number === 0) {
    console.log("zero");
    return 0;
  }

  console.log("before", number);

  const result = f(number - 1);

  console.log("after", number);

  return result + number;
}

console.log(f(3));

    Don’t run it.

    Take your time.

    First, what is the first thing f(3) does?

    It prints:

    before 3

    Then it calls:

    f(2)

    So we get:

    before 3
before 2

    Then:

    f(1)

    Then:

    before 3
before 2
before 1

    Then f(0).

    That call prints:

    zero

    and returns 0.

    But are we finished?

    No.

    Look at the line after the recursive call:

    console.log("after", number);

    Remember: the earlier calls were waiting.

    So after f(0) returns, f(1) continues.

    Then f(2) continues.

    Then f(3) continues.

    The complete output is:

    before 3
before 2
before 1
zero
after 1
after 2
after 3
6

    The returned value is 6.

    This is a good example to trace with a call stack.

    While f(0) is running, the stack looks roughly like:

    f(0)
f(1)
f(2)
f(3)

    f(0) returns.

    Then:

    f(1)
f(2)
f(3)

    f(1) prints "after", 1 and returns.

    Then:

    f(2)
f(3)

    And so on.

    The important thing is that the function calls do not disappear just because they are waiting.

    They remain on the stack.

    They are waiting for the call above them to return.

    Exercises#

    For each exercise, create a separate JavaScript file.

    Do not run the program until you have made a prediction.

    1. Nested calls#

    Write:

    function double(number) {
  return number * 2;
}

function addOne(number) {
  return number + 1;
}

    Then determine the value of:

    addOne(double(10))

    and:

    double(addOne(10))

    Write your predicted answers as comments before running the program.

    2. A function as an argument#

    Write an add function that takes two numbers and returns their sum.

    Then determine the result of:

    add(double(4), addOne(4))

    Trace each inner call before calculating the final result.

    3. Several levels deep#

    Write three functions:

    f
g
h

    where f calls g, and g calls h.

    Call:

    f(5)

    Draw the call stack as the program runs.

    Then draw it again as the functions return.

    4. Draw the stack#

    Without running this program, draw the call stack at its deepest point:

    function a(number) {
  return b(number);
}

function b(number) {
  return c(number);
}

function c(number) {
  return d(number);
}

function d(number) {
  return number + 1;
}

console.log(a(5));

    Then determine the final value.

    5. Recursive mathematics#

    Write a recursive JavaScript function for a mathematical recursive definition you already know.

    For example, you could implement factorial.

    Before running it, write down the sequence of calls for:

    factorial(4)

    6. Trace the returns#

    For:

    function sumTo(number) {
  if (number === 0) {
    return 0;
  }

  return number + sumTo(number - 1);
}

    Trace:

    sumTo(5)

    Write down every call and every returned value.

    7. Predict the output#

    Do not run this program:

    function f(number) {
  if (number === 0) {
    console.log("done");
    return 0;
  }

  console.log("enter", number);

  const result = f(number - 1);

  console.log("leave", number);

  return result + number;
}

console.log(f(3));

    Write the exact output, in order.

    Then draw the call stack at its deepest point.

    Only after you have finished both should you run the program and check your answer.

    The mental model#

    You now have several ways of looking at the same program.

    When you see an expression such as:

    add(double(5), addOne(5))

    you can think in terms of an expression tree.

    The tree shows you which expressions have to be evaluated to produce the final value.

    When those expressions contain function calls, you can think about the call stack.

    The stack shows you which function calls are currently active and which calls are waiting.

    And when a function calls itself, you can use exactly the same model.

    sumTo(4)

    creates a call to sumTo(3).

    That creates a call to sumTo(2).

    That creates a call to sumTo(1).

    And so on.

    There is no special machinery you need to imagine.

    It is still:

    call a function → wait for it to return → continue.

    The difference is simply that the function happens to call itself.

    When you can look at a program and answer:

    What is being evaluated?

    Which function is executing?

    What is waiting?

    What value is this call waiting for?

    What happens when this function returns?

    you are no longer just reading the syntax of a function call.

    You are beginning to see the execution of the program.
