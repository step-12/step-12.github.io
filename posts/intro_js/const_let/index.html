    Const, let, if etc

    September 18, 2026
    Javascript, Variable Declaration, Console.log

    From the REPL to the Editor#

    So far, you have been programming in the REPL.

    You have typed expressions such as:

    5 + 3;

    and:

    10 > 5 && 20 < 30;

    JavaScript evaluates them and the REPL shows you the result.

    You have also spent time drawing expression trees.

    You have learned to look at an expression, break it into smaller expressions, and follow the order in which those expressions are evaluated.

    Now we are going to change something.

    We are going to leave the REPL.

    We are going to write a program in a file.

    And this raises an interesting question:

    What is the difference between typing JavaScript into the REPL and putting JavaScript into a file?

    Let’s find out.

    Setting up VS Code#

    We are going to write our first program in a file.

    For this, we will use VS Code.

    Before we start writing JavaScript, let’s get our workspace ready.

    Open VS Code#

    There are two ways to open VS Code.

    From Spotlight#

    Press:

    ⌘ Space

    This opens Spotlight.

    Type:

    Visual Studio Code

    and press Return.

    VS Code will open.

    From the terminal#

    There is another way that you will find yourself using often.

    Open your terminal and go to:

    workspace/intro_js

    For example:

    cd ~/workspace/intro_js

    Check that you are in the right place:

    pwd

    You should see a path ending in:

    workspace/intro_js

    Now type:

    code .

    What is the .?

    It means the current directory.

    So:

    code .

    is telling VS Code:

    Open this directory as my workspace.

    This is a useful pattern to remember. We will continue using the terminal even though we are now writing our programs in an editor.

    Look at the left side of VS Code.

    You should see the intro_js directory in the Explorer.

    This is where we will keep the programs we write during this section.

    Creating a file#

    In the Explorer, find intro_js.

    Click the New File button.

    Give the file the name:

    program.js

    The file should open in the editor.

    Now type:

    5 + 3;

    You have just written your first program in a file.

    Saving a file#

    Press:

    ⌘ S

    This saves the file.

    You can also save it using File → Save.

    Get into the habit of saving after making a change:

    write → save → run

    We will use this cycle repeatedly.

    Now let’s run the program.

    Open the terminal and make sure you are still in:

    workspace/intro_js

    Then run:

    node program.js

    What happened?

    Nothing.

    You might have expected:

    8

    After all, when you typed 5 + 3 into the REPL, JavaScript showed you 8.

    Why didn’t anything appear this time?

    Before we answer that, change the program to:

    5 + 3;
10 * 4;
20 - 7;

    Run it again.

    Still nothing.

    This is an important difference between the REPL and a program.

    The REPL has a special job:

    Read → Evaluate → Print → Loop

    It evaluates your expression and then prints the result for you.

    A program does not automatically print the result of every expression it evaluates.

    The expressions are still being evaluated.

    There is simply nothing telling Node to display their results.

    We’ll come back to this.

    Running a program#

    You have already learned something about commands, shells and processes.

    When you type:

    node program.js

    the shell sees a command.

    The command is:

    node

    and:

    program.js

    is an argument given to Node.

    Node is a program.

    It starts as a process.

    It receives program.js as an argument, loads the file, and executes the JavaScript inside it.

    So there is nothing mysterious about running a JavaScript program.

    It fits the same model you have already been learning:

    shell
  ↓
starts a process
  ↓
node
  ↓
receives program.js as an argument
  ↓
loads and executes the JavaScript

    The fact that the argument happens to be the name of a JavaScript file does not change how the shell starts the process.

    This is worth noticing.

    You have not left the world of processes and shells.

    You have simply given another program something interesting to do.

    Giving a value a name#

    So far, we have worked with values:

    20;

    and expressions that produce values:

    5 + 3;

    But suppose we calculate something and want to give the result a name.

    For example:

    const age = 20;

    Before we talk about const, look at this differently.

    There is a value:

    20

    and there is a name:

    age

    We want JavaScript to remember that:

    age → 20

    What does that remind you of?

    Think back to Expression Trees Part 2.

    You used a lookup table:

    Name    Value
────    ─────
a       12
b       5
c       3
d       2

    When JavaScript sees a name such as a in an expression, it can look up the name and find its value.

    A variable is a way of putting a name and a value into this table.

    So we can think of:

    const age = 20;

    as an expression tree like this:

           const
       /   \
     age    20

    Or, using the notation you have already used:

    [const, age, 20]

    When this is evaluated, JavaScript creates an entry:

    Name    Value
────    ─────
age     20

    Now we have something new.

    We have a variable.

    A variable is a name associated with a value.

    Naming variables#

    The name of a variable is important.

    You could write:

    const a = 20;

    There is nothing technically wrong with this.

    But what does a mean?

    Compare:

    const a = 20;

    with:

    const age = 20;

    The second one tells a human reader much more.

    Names are part of how we communicate through programs.

    There are rules about what can be used as a variable name.

    For now, follow these conventions:

    const age = 20;
const totalMarks = 87;
const studentName = "Ravi";

    Prefer camel case:

    studentName;
totalMarks;
numberOfStudents;

    Start with a letter.

    You will sometimes see names beginning with _:

    _internalValue;

    There are legitimate uses for this, but don’t reach for _ just because you don’t know what else to call something.

    And $ can technically appear in JavaScript names too:

    $thing;

    You will occasionally encounter this in real programs.

    For our programs, you will almost never need it.

    Most of the time, a good variable name is simply:

    a descriptive word, or several descriptive words written in camel case.

    Why const?#

    Let’s return to:

    const age = 20;

    What happens if we write:

    const age = 20;
const age = 30;

    Run it.

    JavaScript complains.

    Why?

    Look at the table.

    After the first statement:

    Name    Value
────    ─────
age     20

    Now JavaScript encounters:

    const age = 30;

    The tree is:

           const
       /   \
     age    30

    JavaScript tries to create an entry for age.

    But age is already there.

    You cannot create another const with the same name in the same scope.

    So JavaScript stops and reports an error.

    The important thing isn’t the exact wording of the error.

    The important thing is what happened to our table.

    We already had:

    age → 20

    and const says:

    Create this name with this value.

    But the name already exists.

    const also means something else#

    There is another experiment.

    Start with:

    const age = 20;

    Now try:

    age = 30;

    This is different from declaring another variable.

    We aren’t saying:

    Create age.

    We are saying:

    Change the value associated with age.

    Think about our table.

    It currently contains:

    Name    Value
────    ─────
age     20

    An ordinary assignment would try to turn this into:

    Name    Value
────    ─────
age     30

    But age was declared using const.

    const does not allow the variable to be reassigned.

    So JavaScript reports an error.

    The expression tree for the assignment might be thought of as:

           =
      / \
    age  30

    The tree is asking JavaScript to change the table.

    But the declaration has said that this particular name cannot be reassigned.

    So:

    const age = 20;

    means, roughly:

    Create the name age, associate it with 20, and don’t allow age to be reassigned.

    This gives us a useful default.

    Prefer const#

    When you create a variable, start by asking:

    Do I expect this variable to be reassigned later?

    If the answer is no, use:

    const

    This is why you should generally prefer const by default.

    You aren’t telling JavaScript that the value can never exist differently anywhere.

    You are telling JavaScript that this variable name will not be reassigned.

    But sometimes a value needs to change#

    Consider a game.

    A player’s score might start at zero:

    let score = 0;

    and later become:

    10

    then:

    20

    then:

    35

    We need a variable that can be reassigned.

    This is where let comes in.

    let#

    Try:

    let score = 0;

    Think about the tree:

           let
       / \
    score  0

    or:

    [let, score, 0]

    JavaScript evaluates this declaration.

    The table becomes:

    Name     Value
─────    ─────
score      0

    Now try:

    score = 10;

    The assignment changes the table:

    Name     Value
─────    ─────
score     10

    Now:

    score = 20;

    The table becomes:

    Name     Value
─────    ─────
score     20

    And:

    score = score + 5;

    What happens here?

    Look at the expression tree.

    There are really two things happening.

    First:

    score + 5

    must be evaluated.

    JavaScript looks up score:

    score → 20

    so:

    score + 5

    becomes:

    20 + 5

    which produces:

    25

    Then the assignment updates the table:

    Name     Value
─────    ─────
score     25

    This is very similar to what you did in Expression Trees Part 2 when you followed values through a changing lookup table.

    let and declaring again#

    Now try:

    let score = 0;
let score = 10;

    What do you think happens?

    Remember what happened with const.

    The first declaration creates:

    score → 0

    The second declaration tries to create score again.

    That isn’t allowed in the same scope.

    So both const and let create a variable.

    Both prevent you from declaring the same variable again in the same scope.

    The important difference for us right now is:

    const → cannot be reassigned

let   → can be reassigned

    So:

    const age = 20;
age = 21;

    is an error.

    But:

    let age = 20;
age = 21;

    is fine.

    For now, don’t worry about the word scope.

    We will meet that idea when we start putting code inside if statements.

    A small program#

    Let’s put these ideas together.

    Create:

    program.js

    and write:

    const price = 50;
const quantity = 3;

let total = price * quantity;

    Run:

    node program.js

    What appears?

    Nothing.

    But something happened.

    Try tracing the table.

    First:

    const price = 50;

    gives:

    price → 50

    Then:

    const quantity = 3;

    gives:

    price     → 50
quantity  → 3

    Then:

    let total = price * quantity;

    JavaScript evaluates:

    price * quantity

    by looking up the names:

    50 * 3

    which produces:

    150

    The table becomes:

    price     → 50
quantity  → 3
total     → 150

    The program has done real work.

    It just hasn’t displayed anything.

    How do we make it display something?#

    You already know how to ask JavaScript for a value in the REPL.

    For example:

    5 + 3;

    The REPL prints:

    8

    But a program doesn’t have the REPL’s Print step.

    So we need something else.

    Try this:

    console.log("Hello");

    Run:

    node program.js

    Now you get:

    Hello

    We’ve just met console.log.

    console.log#

    Try:

    console.log(5 + 3);

    You should see:

    8

    Notice the difference between these:

    5 + 3;

    and:

    console.log(5 + 3);

    The first evaluates an expression.

    The second calls console.log with the result of that expression.

    You already know about function calls from your Expression Trees work.

    Think about:

    console.log(5 + 3);

    as a tree:

              console.log
               |
              (+)
             /   \
            5     3

    JavaScript evaluates:

    5 + 3

    first.

    That produces:

    8

    Then console.log is called with:

    8

    and the value is written to the terminal.

    Try:

    const price = 50;
const quantity = 3;

let total = price * quantity;

console.log(total);

    Now you finally see:

    150

    But why does the REPL show undefined?#

    There is one small mystery.

    Try this in the REPL:

    console.log("Hello");

    You will probably see something like:

    Hello
undefined

    Why?

    We know that console.log printed:

    Hello

    But what is the second line?

    Remember what the REPL does.

    It evaluates what you type and then prints the result of that evaluation.

    The console.log function itself does not produce an interesting value for us.

    Its result is:

    undefined

    So two different things are happening:

    console.log("Hello")
        ↓
prints "Hello"

the call itself
        ↓
produces undefined

REPL
        ↓
prints undefined

    That is why the REPL can show both:

    Hello
undefined

    The Hello came from console.log.

    The undefined came from the REPL printing the result of the call.

    In a file:

    console.log("Hello");

    there is no REPL sitting there printing the result of every expression.

    So you simply see:

    Hello

    Now we can make a decision#

    We have variables.

    We have values.

    We have expressions.

    We can print things.

    But programs also need to make decisions.

    Suppose:

    const age = 20;

    We want to print:

    Adult

    only if the age is at least 18.

    We already know how to ask JavaScript a question:

    age >= 18;

    That expression produces a boolean.

    So try this:

    const age = 20;

if (age >= 18) {
  console.log("Adult");
}

    Run it.

    You should see:

    Adult

    Now change:

    const age = 15;

    Run it again.

    What happened?

    Nothing.

    This is something new.

    Earlier, when we evaluated an expression, JavaScript evaluated the expression.

    Here, JavaScript did not necessarily evaluate everything.

    It first evaluated:

    age >= 18;

    If the answer was true, it evaluated the code inside the braces.

    If the answer was false, it skipped that code.

    An if is different#

    Think back to our expression trees.

    For an ordinary expression such as:

    5 + 3;

    the tree contains the parts that need to be evaluated:

          +
     / \
    5   3

    For an if, we can think of the structure as:

    [if, predicate, then part, else part]

    For example:

    if (age >= 18) {
  console.log("Adult");
}

    can be thought of as:

                 if
          /      \
     predicate   then
         |         |
     age >= 18   console.log(...)

    There is something fundamentally different here.

    The predicate is evaluated first.

    Suppose:

    age >= 18

    produces:

    false

    Then the then part is not evaluated.

    It is skipped.

    This is different from an ordinary expression.

    When we had:

    5 + 3;

    both 5 and 3 were needed to calculate the result.

    With:

    if (age >= 18) {
  console.log("Adult");
}

    the code inside the if only matters when the condition is true.

    This is the beginning of control flow.

    The program is no longer simply evaluating one expression after another.

    The result of one evaluation can determine what gets evaluated next.

    Adding else#

    Our program currently says:

    If the person is an adult, print Adult.

    But what if they aren’t?

    We can add another branch:

    const age = 15;

if (age >= 18) {
  console.log("Adult");
} else {
  console.log("Not an adult");
}

    Now think about the tree:

                 if
          /      \
    predicate    then
       |           |
   age >= 18   console.log(...)


              else
                |
          console.log(...)

    Or more compactly:

    [if, predicate, then part, else part]

    What happens when the predicate is true?

    The then part is evaluated.

    The else part is skipped.

    What happens when the predicate is false?

    The then part is skipped.

    The else part is evaluated.

    Not both.

    This is the important idea.

    An if is not merely another way of calculating a value.

    It controls which code gets executed.

    Try making the decision yourself#

    Start with:

    const number = 10;

    Can you write a program that prints:

    positive

    if the number is greater than zero?

    Start with only the if.

    Then add an else.

    Then try:

    const number = -5;

    What happens?

    Now try:

    const number = 0;

    Should it print positive?

    If not, how would you change the predicate?

    Don’t immediately look for the answer.

    Write the expression.

    Predict what it will do.

    Run it.

    Investigate.

    if and the conditional expression#

    You have already seen another way of making a choice.

    In the REPL you wrote things like:

    true ? "yes" : "no";

    and:

    10 % 2 === 0 ? "even" : "odd";

    This is called the conditional expression, or more commonly the ternary operator.

    It looks like:

    condition ? valueIfTrue : valueIfFalse

    For example:

    const result = age >= 18 ? "adult" : "minor";

    The important word here is value.

    The ternary chooses between values.

    The result of:

    age >= 18 ? "adult" : "minor";

    is one value:

    "adult"

    or:

    "minor"

    This makes ternaries useful when you are choosing a value.

    For example:

    const message = age >= 18 ? "adult" : "minor";

    This is a good use of a ternary.

    When should you use if?#

    Now consider:

    if (age >= 18) {
  console.log("Adult");
} else {
  console.log("Minor");
}

    There isn’t a value we are trying to choose here.

    We are deciding which code should run.

    That is what if is good at.

    A useful distinction is:

    Ternary: choose a value.

    if: choose which code executes.

    Consider this:

    const message = age >= 18 ? "adult" : "minor";

    The ternary makes sense because we are choosing the value of message.

    But this:

    age >= 18 ? console.log("Adult") : console.log("Minor");

    is awkward.

    We aren’t really choosing between values.

    We are choosing which actions to perform.

    An if communicates that much more clearly:

    if (age >= 18) {
  console.log("Adult");
} else {
  console.log("Minor");
}

    On the other hand, this is unnecessarily long:

    let message;

if (age >= 18) {
  message = "adult";
} else {
  message = "minor";
}

    We are simply choosing one of two values.

    This is a good place for a ternary:

    const message = age >= 18 ? "adult" : "minor";

    So don’t think:

    Ternary is short, if is long.

    Instead ask:

    Am I choosing a value, or am I choosing which code gets executed?

    That question will usually point you in the right direction.

    One more experiment#

    Try:

    const number = 10;

if (number > 5) {
  console.log("A");
  console.log("B");
  console.log("C");
}

    What happens?

    Now change it to:

    const number = 2;

    What happens?

    Notice that the if controls an entire section of code.

    This is another reason not to think of if simply as a fancy expression.

    It controls execution.

    The expression:

    number > 5;

    produces a value.

    That value determines what happens next.

    What have we added to our mental model?#

    When we started, our mental model looked something like:

    values
   ↓
expressions
   ↓
evaluation
   ↓
new values

    Variables add a lookup table:

                 lookup table
             ┌─────────────┐
             │ age → 20    │
             │ score → 50  │
             └─────────────┘
                    ↑
                    │
              name lookup
                    │
              expressions

    const and let give names entries in that table.

    const says:

    create this name
and don't reassign it

    let says:

    create this name
and allow it to be reassigned

    console.log gives us a way to deliberately produce output.

    And if introduces something new:

    evaluate a condition
        ↓
choose which code runs

    That last part is particularly important.

    Until now, most of our programming has been about:

    What value does this expression produce?

    Now we can start asking:

    What should the program do next?

    That is a much bigger question.

    Small exercises#

    Do these in program.js.

    Don’t solve all of them at once.

    For each one:

    1. Write the program.
    2. Predict what it will do.
    3. Run it with node program.js.
    4. If you were surprised, investigate.

    1. A named calculation#

    Create:

    const width = 10;
const height = 5;

    Create another variable containing the area of the rectangle.

    Print the area.

    2. Change the value#

    Create:

    let score = 0;

    Then change the score three times.

    For example:

    0 → 10 → 25 → 40

    Print the final score.

    3. Const experiment#

    Write a program that declares a variable using const.

    Try to declare it again.

    What error do you get?

    Then start again and try to reassign it.

    What is different about the two errors?

    4. Let experiment#

    Create:

    let number = 10;

    Then change it to:

    20
30
40

    Print the final value.

    Now try declaring number again with let.

    What happens?

    5. Even or odd#

    Create:

    const number = 17;

    Use if and % to print:

    even

    or:

    odd

    depending on the number.

    Try several numbers.

    6. Positive, negative or zero#

    Create:

    const number = -5;

    Print one of:

    positive
negative
zero

    You will need more than one if.

    Think carefully about the order in which the decisions should happen.

    7. Adult or minor#

    Create:

    const age = 17;

    Print:

    adult

    if the age is 18 or above.

    Otherwise print:

    minor

    Try both an if and an if/else.

    8. Ternary or if?#

    For each problem, decide whether you would use a ternary or an if.

    Don’t write the program yet.

    A.

    Choose "pass" or "fail" and store it in a variable.

    B.

    Print "Starting...", perform some other operation, and then print "Finished." only when a condition is true.

    C.

    Choose "even" or "odd" and store the answer in a variable.

    D.

    Print a warning if a value is outside an allowed range.

    Explain your choice.

    9. Expression trees#

    Draw the expression tree for:

    const total = 10 + 5;

    Then draw the tree for:

    let score = score + 10;

    What is different between the two?

    What happens to the lookup table in each case?

    10. Follow the table#

    Start with:

    let score = 10;
let bonus = 5;

    Then:

    score = score + bonus;
bonus = score * 2;
score = score + bonus;

    Draw the lookup table after every statement.

    What is the final value of score?

    Can you trace the entire program using the same table-following technique you used in Expression Trees Part 2?

    One last habit#

    You now have a few more pieces of the language.

    But the most important habit hasn’t changed.

    When you see:

    const total = price * quantity;

    don’t just read it as English.

    Look at its structure.

    What is the tree?

    What values need to be looked up?

    What gets evaluated first?

    What happens to the table?

    And when you see:

    if (score >= 50) {
  console.log("Pass");
}

    ask a slightly different question:

    Which parts of this program will actually be evaluated?

    That is the new idea.

    Until now, you have mostly followed evaluation.

    Now you are beginning to follow execution.

    The REPL helped you learn to ask:

    What value does this expression produce?

    The editor will now help you learn to ask:

    What does this program do?
