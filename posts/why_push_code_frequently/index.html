      Why Should We Push Code Frequently?

      October 15, 2026
      Git, Github, Gacp, Raylib-Assignments

      Why Should We Push Code Frequently?#

      You are currently working on the Marvellous Filters assignment.

      You are trying different techniques to manipulate Wolverine’s image.

      Some techniques work. Some don’t.

      But what happens to your previous working code when you try something new?

      What If Your Previous Technique Was Better?#

      Suppose you’re working on Sentinel assignment.

      After experimenting for some time, you manage to flip Wolverine’s image upside down.

      It works!

      But you think there might be a simpler way to implement it.

      So you change your code.

      After another hour of experimenting, you realize your previous implementation was better.

      Now, how do you get it back?

      Can you remember every detail of the previous implementation?

      The loops? The indexes? The conditions?

      What if you made several changes since then?

      Wouldn’t it be useful to preserve every working version before trying something different?

      Should We Create Another File?#

      One way to preserve our previous implementation is to create another file.

      mirror.js
mirror_new.js
mirror_new_2.js
mirror_final.js
mirror_final_new.js

      But how many files are we going to create?

      And which one contains the correct implementation?

      What if you want to compare two techniques?

      Do you open every file and manually figure out what changed?

      We already have Git to maintain the history of our code.

      We don’t need to create _new files just to preserve previous implementations.

      Can’t We Just Undo?#

      What about Cmd + Z?

      It can undo recent edits.

      But what if you want the implementation you wrote yesterday?

      What if you closed the editor, changed several files, and tried multiple approaches?

      Can you rely on Undo to recover that working version?

      Not reliably.

      Git allows us to return to previous committed versions and compare what changed.

      But there is one important catch.

      If you never committed that working version, Git cannot bring it back.

      When Should We Push?#

      Should we push only after completing the entire assignment?

      Or after solving each problem?

      Why wait that long?

      Suppose you’re still working on The Rotator.

      Your first implementation correctly creates a new bitmap with the expected dimensions.

      The rotation logic isn’t complete yet, but this part works.

      You can preserve it.

      gacp "create rotated bitmap dimensions"

      Now you work on rearranging the pixels.

      After some experimentation, you manage to rotate a small test bitmap correctly.

      Another working version!

      gacp "rotate test bitmap clockwise"

      You continue improving it until Wolverine’s image rotates correctly.

      gacp "rotate wolverine clockwise"

      Notice something?

      You didn’t wait until the entire problem was complete.

      You preserved your code whenever you reached a meaningful working version.

      Your history might look like this:

      ● rotate wolverine clockwise
● rotate test bitmap clockwise
● create rotated bitmap dimensions
● display original bitmap

      Each checkpoint gives you something to return to.

      And because you pushed, those checkpoints are available on GitHub too.

      How Will Someone Review Your Code?#

      Imagine you’re stuck halfway through a problem.

      You want your mentors/peers to review your implementation.

      But the latest code on GitHub is from two days ago or not even pushed to github.

      How will they see what you’re currently working on?

      Will you send screenshots?

      Copy and paste your code?

      Or ask them to wait until you finish the assignment?

      If you’ve been pushing your working versions, your mentor/peers can inspect your progress directly.

      They can see what you’ve tried, compare implementations, and understand where you’re stuck.

      You don’t have to finish an assignment to get your code reviewed.

      How Do You Measure Your Progress?#

      You’ve been working on Wolverine for several days.

      What have you accomplished so far?

      What techniques have you tried?

      Which problems did you encounter?

      What did you improve?

      It’s difficult to remember every small change.

      But if you’ve been creating meaningful checkpoints, your Git history helps answer these questions.

      git log --oneline

      You can see how your implementation evolved.

      Not every commit represents a completed problem.

      Some represent small improvements, bug fixes, or working experiments.

      And that’s useful too.

      A Habit Worth Building#

      Whenever you reach a meaningful working version:

      1. Run your code and verify what works.
      2. Push that version using gacp with a meaningful message.
      3. Continue experimenting.

      You don’t need to push after every line of code.

      You also don’t need to wait until the entire problem or assignment is complete.

      Push after every meaningful working version.

      Something to Think About#

      You’re working on a problem.

      After two hours of experimenting, you finally get something working.

      You feel you can improve it further.

      What should you do before changing the implementation?

      And if your next approach doesn’t work, how will you recover the previous one?

      Remember:

      Your working code is a checkpoint, not something you should casually throw away.

      Preserve it. Push it. Then experiment further.
