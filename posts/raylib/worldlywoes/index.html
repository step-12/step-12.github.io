      Worldly Woes

      October 13, 2026
      Raylib, Graphics, Organization

      The Woes Of The World#

      When we started writing Raylib programs, I gave you a template that used a world object.

      The idea was simple. We needed a way to share information between setup(), update(), and draw(). So setup() would create a world, and the other functions would use it.

      This was a reasonable idea.

      Unfortunately, the world has grown in power. It now knows everything, goes everywhere, and is invited to functions that have absolutely no business meeting it.

      Let’s look at some of the problems this creates.

      1. The world is a junk drawer#

      Consider a program that draws a player and an enemy on the screen.

      We might start with something like this:

      const world = {
  screenWidth: 800,
  screenHeight: 600,

  playerX: 100,
  playerY: 200,
  playerSpeed: 5,

  enemyX: 300,
  enemyY: 100,
  enemySpeed: 2,

  score: 0,
  fontSize: 20,
};

      This works. There is nothing inherently wrong with the code.

      But look at the structure. We have a collection of unrelated properties sitting next to each other. What belongs to the player? What belongs to the enemy? Which properties describe the screen?

      We have to figure this out from the names.

      Now consider a different structure:

      const world = {
  screen: {
    width: 800,
    height: 600,
  },

  player: {
    x: 100,
    y: 200,
    speed: 5,
  },

  enemy: {
    x: 300,
    y: 100,
    speed: 2,
  },

  score: 0,
  fontSize: 20,
};

      The information is the same. The organization is different.

      We can now talk about world.screen, world.player, and world.enemy. Each group has a clear meaning.

      Notice that score and fontSize are still at the top level. That’s fine for now. We don’t need to create a nested object for every property. We group things when the grouping communicates something useful.

      A useful structure tells us how the information belongs together.

      Imagine what happens when we add more players:

      player2X;
player2Y;
player2Speed;

player3X;
player3Y;
player3Speed;

      Perhaps the world is trying to tell us something.

      Rule of thumb: Group related properties together. Don’t turn your world into a junk drawer.

      2. The world must attend every meeting#

      Let’s write a function that draws a rectangle in the centre of the screen.

      We know the screen dimensions. The rectangle is 100 pixels wide and 50 pixels tall.

      function drawRectangle(world) {
  const x = (world.screen.width - 100) / 2;
  const y = (world.screen.height - 50) / 2;

  r.DrawRectangle(x, y, 100, 50, r.RED);
}

      And we call it like this:

      drawRectangle(world);

      Does this work? Yes.

      Does the function need the entire world? No.

      It needs the dimensions of the screen. It doesn’t care about the player, the enemy, the score, or your plans for the weekend.

      Let’s change the function:

      function drawRectangle(screen) {
  const x = (screen.width - 100) / 2;
  const y = (screen.height - 50) / 2;

  r.DrawRectangle(x, y, 100, 50, r.RED);
}

      And call it like this:

      drawRectangle(world.screen);

      Much better. The function receives exactly the information it needs.

      This is useful for another reason. Suppose we want to use drawRectangle() in a different program. We don’t have to recreate our entire world object just to draw a rectangle. We only need to provide an object with the screen dimensions.

      Rule of thumb: Pass the smallest meaningful piece of information that a function needs.

      This doesn’t mean you must always pass individual numbers. If a function needs a screen’s width and height, passing the screen object is perfectly reasonable. It keeps related information together.

      It also doesn’t mean passing world is always wrong. Some functions genuinely need to coordinate several parts of the program.

      But if a function needs only one small part of the world, pass that part.

      The world has other things to do. Stop making it attend every meeting.

      3. The world gives us terrible APIs#

      This is where things get interesting.

      Suppose we want to move the player horizontally.

      We might write:

      function movePlayer(world) {
  world.player.x += world.player.speed;
}

      And call it from update():

      function update(world) {
  movePlayer(world);
}

      This works, but look at the function. It knows that the player lives inside world, and it knows the exact structure of that world.

      Now suppose we want to move the enemy too.

      We could write another function:

      function moveEnemy(world) {
  world.enemy.x += world.enemy.speed;
}

      We now have two functions doing essentially the same thing. The only difference is which object they operate on.

      What if we wrote the function around the operation instead?

      function move(object) {
  object.x += object.speed;
}

      Now we can call it like this:

      function update(world) {
  move(world.player);
  move(world.enemy);
}

      The function doesn’t know about the world. It doesn’t know whether the object is a player, an enemy, or something else entirely.

      It only knows that the object has an x property and a speed property.

      This is a better API because the function describes what it does, rather than where its data happens to live.

      We could use the same function for another object without changing the function itself.

      Congratulations. We have stopped writing separate functions because our first function was too attached to the name of its employer.

      There is an important distinction here: move() changes the object it receives. In this example, that is intentional because update() is responsible for changing the state of our sketch. Passing an object to a function does not automatically mean the function should modify it; that decision should be deliberate.

      Rule of thumb: Design functions around the job they perform, not around the structure of the world that happens to contain their data.

      4. Does every function need the world?#

      Let’s look at a few more functions.

      function drawBackground(world) {
  r.ClearBackground(world.background);
}

function drawScore(world) {
  r.DrawText(String(world.score), 10, 10, world.fontSize, r.WHITE);
}

function calculateCentre(world) {
  return {
    x: world.screen.width / 2,
    y: world.screen.height / 2,
  };
}

      All three functions receive world. But do they need it?

      Let’s look at what each function actually uses.

      drawBackground() needs the background colour.

      drawScore() needs the score and font size.

      calculateCentre() needs the screen dimensions.

      We could make the dependencies clearer:

      function drawBackground(background) {
  r.ClearBackground(background);
}

function drawScore(score, fontSize) {
  r.DrawText(String(score), 10, 10, fontSize, r.WHITE);
}

function calculateCentre(screen) {
  return {
    x: screen.width / 2,
    y: screen.height / 2,
  };
}

      And call them like this:

      drawBackground(world.background);

drawScore(world.score, world.fontSize);

const centre = calculateCentre(world.screen);

      Each function now tells us what it needs through its parameters.

      This is not just about saving a few characters. A function that accepts world can potentially depend on anything inside it. A function that accepts screen can depend on the screen information it receives.

      That difference matters when programs grow. If you change the structure of world, you may have to change every function that depends on it. Smaller, more deliberate interfaces reduce that coupling.

      Of course, there is no need to go overboard. If a function genuinely needs several related properties, pass the object containing those properties. We don’t need to pass six separate arguments when one well-designed object will do.

      The goal is clarity, not the smallest possible parameter list.

      5. So, what should a world look like?#

      There is no universal structure that every world must follow. The structure depends on what your program represents.

      For a sketch that draws a player, an enemy, and a score, this is a reasonable starting point:

      function setup() {
  return {
    screen: {
      width: 800,
      height: 600,
    },

    player: {
      x: 100,
      y: 200,
      speed: 5,
    },

    enemy: {
      x: 300,
      y: 100,
      speed: 2,
    },

    score: 0,
    background: r.BLACK,
    fontSize: 20,
  };
}

      The important thing is not that you have nested objects. The important thing is that the structure communicates the concepts in your program.

      A screen describes the screen. A player describes the player. An enemy describes the enemy. The world brings together the information needed by the sketch.

      When writing a function, ask yourself:

      • What information does this function need?
      • Does it need the whole world, or just one part?
      • Could the function be useful in another program without knowing about this particular world?
      • Am I making the function depend on information it has no reason to know about?

      These questions will help you design better interfaces.

      6. An exercise: Who needs the world?#

      Consider this world:

      const world = {
  screen: {
    width: 800,
    height: 600,
  },

  player: {
    x: 100,
    y: 200,
    speed: 5,
  },

  score: 0,
  background: r.BLACK,
  fontSize: 20,
};

      For each function below, decide what arguments it should receive.

      drawBackground(...)
drawPlayer(...)
calculateCentre(...)
move(...)
drawScore(...)

      For each function, write down:

      1. What information does it need?
      2. What should its parameters be?
      3. Why does it need those parameters? Would passing the entire world be justified?

      You don’t need to write the function implementations. Focus on designing their interfaces.

      Once you’re done, compare your answers with a friend. You may arrive at different designs, but you should be able to explain why your design makes sense.

      Conclusion#

      The world object is a useful convention. It gives us a convenient place to keep the state of our sketch and pass that state between setup(), update(), and draw().

      But convenience can become a problem when we stop thinking about what belongs in the world and what each function actually needs.

      Group related information. Give objects meaningful structure. Pass functions the information they need. Design functions around their purpose.

      And remember: just because a function can receive the entire world doesn’t mean it should.

      The world is already a big place. Let’s not make it any bigger than it needs to be.
