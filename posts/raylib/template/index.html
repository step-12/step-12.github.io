    Raylib, Organization

    Modules and a Raylib Template#

    So far, each Raylib program you have written has lived in a single file.

    We have already started organizing that file into functions:

    function setup() {}

function update() {}

function draw() {}

function loop() {
  while (!r.WindowShouldClose()) {
    update();
    draw();
  }
}

function main() {
  setup();
  loop();
}

main();

    This gives different parts of the program different responsibilities.

    But there is another kind of organization available to us.

    We can separate our program into different files.

    To understand how, we first need to learn about modules.

    A Small Module#

    Create a directory:

    ~/workspace/modules

    Inside it, create two files:

    modules/
├── main.js
└── numbers.js

    Put this in numbers.js:

    function double(n) {
  return n * 2;
}

module.exports = {
  double,
};

    There is one new thing here:

    module.exports = {
  double,
};

    We are saying that the function double should be available to other files.

    We say that we are exporting double.

    Now go to main.js.

    Write:

    const numbers = require("./numbers");

console.log(numbers);

    Run the program.

    Look carefully at what is printed.

    Now change it to:

    const numbers = require("./numbers");

console.log(typeof numbers);

    What do you get?

    You should see:

    object

    require() returns something.

    In this case, it returns an object.

    The object contains the things that numbers.js exported.

    So we can write:

    const numbers = require("./numbers");

console.log(numbers.double(5));

    This should print:

    10

    There are two sides to what just happened.

    In numbers.js:

    module.exports = {
  double,
};

    we export something.

    In main.js:

    const numbers = require("./numbers");

    we require that module.

    Then:

    numbers.double(5);

    uses something provided by the module.

    More Than One Function#

    Add another function to numbers.js:

    function double(n) {
  return n * 2;
}

function square(n) {
  return n * n;
}

module.exports = {
  double,
  square,
};

    Now try:

    const numbers = require("./numbers");

console.log(numbers.double(5));
console.log(numbers.square(5));

    The object returned by require() now gives us both functions:

    numbers
   ├── double
   └── square

    A module can provide several things to another part of our program.

    A Function We Have Already Reused#

    Think back to the first Raylib exercises.

    You had to centre a rectangle in the window.

    You eventually wrote a function similar to:

    function calcOffset(outer, inner) {
  return (outer - inner) / 2;
}

    Then you had to centre one rectangle inside another rectangle.

    The same calculation appeared again.

    Then you scaled a rectangle and centred it.

    Again, you needed the same calculation.

    We solved one problem already.

    Instead of repeating:

    (outer - inner) / 2;

    everywhere, we put the calculation in a function.

    Now suppose you have several different programs:

    01_center_rectangle.js
02_center_rectangle_in_rectangle.js
03_scale_and_center.js

    Each program could contain its own copy of calcOffset().

    But now we are repeating something again.

    Not the calculation this time.

    The function itself.

    Reusing a Function Across Programs#

    Create a file called:

    geometry.js

    Put the function in it:

    function calcOffset(outer, inner) {
  return (outer - inner) / 2;
}

module.exports = {
  calcOffset,
};

    Now another file can use it:

    const geometry = require("./geometry");

const x = geometry.calcOffset(400, 200);

console.log(x);

    The function no longer needs to belong to one particular Raylib program.

    It belongs to geometry.js.

    Any program that needs the calculation can require the module.

    This gives us another kind of reuse.

    First we learned:

    repeated calculation
        ↓
      function

    Now we have:

    useful function
        ↓
      module
        ↓
used by different programs

    A function lets us reuse a computation.

    A module lets us reuse functions across files.

    A Small Library#

    We have just created a module called geometry.js.

    It contains a function that is useful to more than one program:

    function calcOffset(outer, inner) {
  return (outer - inner) / 2;
}

module.exports = {
  calcOffset,
};

    There is another word you will hear when talking about reusable code:

    library.

    A library is code that has been written so that other programs can use it.

    Our geometry.js is a very small library.

    It is also a module.

    These words are related, but they are not quite the same thing.

    A module is a unit of code that can be used by another part of a program.

    A library is reusable code intended to be used by other programs.

    For now, you don’t need to worry too much about the distinction.

    Just remember:

    module
   ↓
a reusable unit of code

library
   ↓
reusable code that programs can use

    Our geometry library might eventually contain several useful functions:

    function calcOffset(outer, inner) {
  return (outer - inner) / 2;
}

function distance(x1, y1, x2, y2) {
  // ...
}

function intersects(a, b) {
  // ...
}

module.exports = {
  calcOffset,
  distance,
  intersects,
};

    Different programs can require the library and use whichever functions they need.

    You have already been using a library without thinking about it.

    When we write:

    const r = require("raylib");

    we are requiring the Raylib library.

    Raylib provides us with functions for creating windows, drawing shapes, reading input, and many other things.

    So there is nothing mysterious about a library.

    It is simply useful code that someone else has written and made available for our programs to use.

    We will build some small libraries of our own as we continue.

    Back to Our Raylib Skeleton#

    Now return to the skeleton we have been using.

    We previously separated the program into:

    setup
update
draw
loop
main

    These functions do not all have the same responsibility.

    setup() prepares our particular program.

    update() changes our particular program.

    draw() displays our particular program.

    But loop() is different.

    It is the machinery that repeatedly does this:

    update();
draw();

    And main() is the machinery that starts everything.

    There is a useful boundary here.

    We can put the code that describes our particular drawing or animation in one file.

    We will call that file:

    sketch.js

    And we can put the machinery that runs the sketch in:

    main.js

    Our program will become:

    main.js
sketch.js

    Creating sketch.js#

    Start with:

    const r = require("raylib");

function setup() {}

function update() {}

function draw() {}

module.exports = {
  setup,
  update,
  draw,
};

    There is nothing surprising here anymore.

    sketch.js contains three functions.

    It exports them.

    Therefore another file can require sketch.js and receive an object containing those functions.

    Using the Sketch#

    Now create main.js.

    Start with:

    const sketch = require("./sketch");

console.log(typeof sketch);

    What should this print?

    Think about it before running the program.

    Run it.

    You should see:

    object

    Now we can access:

    sketch.setup;
sketch.update;
sketch.draw;

    And we can call them:

    sketch.setup();
sketch.update();
sketch.draw();

    Our functions are in one file.

    The code using them is in another.

    Rebuilding the Loop#

    Now we can write:

    const sketch = require("./sketch");

function loop() {
  while (sketch.running()) {
    sketch.update();
    sketch.draw();
  }
}

    There is a problem.

    We haven’t written running() yet.

    That is deliberate.

    The loop should not need to know that we are using Raylib.

    Think about what the loop actually needs to know.

    It needs to know:

    Should I keep running?

    It doesn’t need to know why.

    The answer to that question belongs to the sketch.

    So add this to sketch.js:

    function running() {
  return !r.WindowShouldClose();
}

    And export it:

    module.exports = {
  running,
  setup,
  update,
  draw,
};

    Now main.js can simply ask:

    while (sketch.running()) {
  sketch.update();
  sketch.draw();
}

    Notice something important.

    main.js does not contain:

    require("raylib");

    It does not know about:

    r.WindowShouldClose();

    It doesn’t know that there is a Raylib window at all.

    It only knows that the sketch can tell it whether it should keep running.

    This is a useful boundary.

    One More Part: Teardown#

    There is one part of our program that we have not given a name yet.

    At the beginning of the program we do some work once:

    setup();

    Then we repeatedly update and draw:

    loop();

    Eventually the loop finishes.

    The program needs to clean things up.

    We will call this:

    teardown();

    For now, it is very small:

    function teardown() {
  r.CloseWindow();
}

    Add it to sketch.js.

    The complete file now looks like this:

    const r = require("raylib");

function running() {
  return !r.WindowShouldClose();
}

function setup() {}

function update() {}

function draw() {}

function teardown() {
  r.CloseWindow();
}

module.exports = {
  running,
  setup,
  update,
  draw,
  teardown,
};

    Why create a whole function for one line?

    For the same reason that we created an empty update() earlier.

    We are creating a place for a particular responsibility.

    Today teardown means:

    r.CloseWindow();

    Later a program may have other things that need to be cleaned up or finished before it exits.

    We now have a place for them.

    Our program has a lifecycle:

    setup
  ↓
loop
  ↓
teardown

    Inside the loop:

    update → draw
  ↑       ↓
  └───────┘

    setup() happens once at the beginning.

    update() and draw() happen repeatedly.

    teardown() happens once at the end.

    main()#

    Now we can write main():

    function main() {
  sketch.setup();
  loop();
  sketch.teardown();
}

    And finally:

    main();

    Our complete main.js is now:

    const sketch = require("./sketch");

function loop() {
  while (sketch.running()) {
    sketch.update();
    sketch.draw();
  }
}

function main() {
  sketch.setup();
  loop();
  sketch.teardown();
}

main();

    Look at this file carefully.

    There is nothing Raylib-specific in it.

    main.js does not import Raylib.

    It does not create a window.

    It does not close a window.

    It does not draw anything.

    It does not know what kind of program it is running.

    It only knows about the lifecycle of a program:

    setup
  ↓
running?
  ↓
update → draw
  ↑       ↓
  └───────┘
  ↓
teardown

    The sketch provides the details.

    This is a much more useful separation than simply putting different functions into different files.

    Warning: Keep Your State in the Sketch#

    There is one important rule to remember as you move your existing programs into this structure.

    Do not put your program’s variables in main.js.

    For example, suppose your program has a rectangle that moves:

    let x = 100;
let y = 100;
let speed = 2;

    It may be tempting to put these variables in main.js because main.js is running the program.

    Don’t.

    These variables describe the state of your sketch.

    They belong in sketch.js:

    const r = require("raylib");

let x = 100;
let y = 100;
let speed = 2;

function running() {
  return !r.WindowShouldClose();
}

function setup() {
  // ...
}

function update() {
  x += speed;
}

function draw() {
  // ...
}

function teardown() {
  r.CloseWindow();
}

module.exports = {
  running,
  setup,
  update,
  draw,
  teardown,
};

    main.js should remain concerned with the lifecycle of the program:

    setup
  ↓
running?
  ↓
update
  ↓
draw
  ↓
running?
  ↓
...
  ↓
teardown

    The variables that describe what is happening belong to the sketch.

    A useful question to ask is:

    Does this variable describe the machinery that runs the program, or does it describe the thing I am building?

    If it describes the thing you are building, it belongs in sketch.js.

    This keeps main.js generic.

    You should be able to take the same main.js and use it with a completely different sketch without changing it.

    That is one of the reasons we separated the files in the first place.

    Put Something in the Sketch#

    An empty sketch is not very interesting.

    Move one of your existing Raylib programs into this structure.

    For example, sketch.js might contain the state for a rectangle:

    const r = require("raylib");

const screenWidth = 400;
const screenHeight = 400;
const FPS = 60;

let rectWidth = 200;
let rectHeight = 200;

function running() {
  return !r.WindowShouldClose();
}

function setup() {
  r.InitWindow(screenWidth, screenHeight, "Rectangle");
  r.SetTargetFPS(FPS);
}

function update() {
  rectWidth++;
  rectHeight--;
}

function draw() {
  // draw the rectangle
}

function teardown() {
  r.CloseWindow();
}

module.exports = {
  running,
  setup,
  update,
  draw,
  teardown,
};

    Fill in draw() yourself.

    You have already solved this problem.

    And remember: if you need your centering calculation, you already know how to move that calculation into geometry.js and require it.

    A Useful Structure#

    We now have three different kinds of code.

    main.js

    contains the machinery that runs our program.

    sketch.js

    contains the particular thing we are currently building.

    geometry.js

    can contain useful geometry calculations that several programs may need.

    These files exist because the code has different responsibilities.

    Do not separate code into files merely because you can.

    Ask:

    What belongs together?

    and:

    What might be useful somewhere else?

    The boundaries come first.

    The files follow those boundaries.

    We Keep Writing the Same main.js#

    There is something interesting about main.js.

    Look at it again:

    const sketch = require("./sketch");

function loop() {
  while (sketch.running()) {
    sketch.update();
    sketch.draw();
  }
}

function main() {
  sketch.setup();
  loop();
  sketch.teardown();
}

main();

    Suppose tomorrow you want to write a program that draws circles.

    Will main.js change?

    Probably not.

    Suppose you want to animate a rectangle.

    Will main.js change?

    Probably not.

    Suppose you want to draw several moving shapes.

    Again, main.js probably does not need to change.

    We have discovered some code that we will use again and again.

    We could copy it manually every time.

    But we can do something better.

    We can make ourselves a template.

    Create a Raylib Template#

    Create a new directory:

    mkdir ~/workspace/raylib_template

    Inside it, create:

    raylib_template/
├── main.js
├── sketch.js
└── geometry.js

    Put the reusable main.js into the template.

    Your sketch.js should contain the structure:

    const r = require("raylib");

function running() {
  return !r.WindowShouldClose();
}

function setup() {
  // prepare the sketch
}

function update() {
  // change the state
}

function draw() {
  // draw the current state
}

function teardown() {
  r.CloseWindow();
}

module.exports = {
  running,
  setup,
  update,
  draw,
  teardown,
};

    And geometry.js can begin with the useful calculation we have already discovered:

    function calcOffset(outer, inner) {
  return (outer - inner) / 2;
}

module.exports = {
  calcOffset,
};

    Your template is now a small program with most of its structure already in place.

    Notice the division:

    main.js
    |
    | knows only about the lifecycle
    ↓
sketch.js
    |
    | knows about Raylib
    ↓
Raylib

    main.js doesn’t care what is happening inside the sketch.

    This is useful because the machinery for running a sketch can now remain unchanged while the sketch itself changes.

    Starting a New Project#

    Suppose you want to start a new project called:

    moving_circle

    You do not need to create all these files again.

    You already have a starting point.

    Run:

    cp -R ~/workspace/raylib_template ~/workspace/moving_circle

    Now look inside:

    moving_circle/
├── main.js
├── sketch.js
└── geometry.js

    You have a complete copy of the template.

    Go into the new project:

    cd ~/workspace/moving_circle

    Now start working on sketch.js.

    Fill in:

    setup();
update();
draw();
teardown();

    You should usually not need to rewrite main.js.

    If you need the centering calculation, use the function in geometry.js.

    If you discover another useful geometry calculation that belongs there, you can add it.

    What We Have Done#

    There are several ideas connected here.

    We started with a calculation:

    (outer - inner) / 2

    We wanted to reuse it, so we made a function.

    Then we wanted to reuse that function in different files, so we made a module.

    Then we noticed that our Raylib skeleton already had useful boundaries:

    setup
update
draw
loop
main

    We used modules to make those boundaries visible in our files.

    We also added two new ideas:

    running()
teardown()

    running() hides the question of how we know whether the program should continue.

    teardown() gives us a place to clean things up when the program finishes.

    So the life of our program is now:

    setup
  ↓
running?
  ↓
update → draw
  ↑       ↓
  └───────┘
  ↓
teardown

    Finally, we noticed that much of this structure does not change from one program to another.

    So we made a template.

    There is a pattern here:

    repeat a calculation
        ↓
make a function
        ↓
reuse the function
        ↓
make a module
        ↓
separate program responsibilities
        ↓
make the structure reusable
        ↓
make a template

    Each time, we notice something we are doing repeatedly.

    Then we give it a place.

    That is one of the ways programs grow without becoming a pile of repeated code.

    Try It#

    Go back to the Raylib exercises you have written so far.

    This time, don’t treat each exercise as a separate program that happens to work.

    Treat them as a collection of programs and look for things that can be reused.

    For each exercise:

    1. Make a fresh copy of raylib_template.
    2. Put the code specific to that exercise into sketch.js.
    3. Keep main.js unchanged.
    4. Look for calculations or functions that are useful in more than one exercise.
    5. Move those functions into appropriate modules.
    6. Use require() to use those modules from your sketch.

    You have already seen one example of this with the centering calculation.

    Now look for other common mathematics.

    For example, you may find calculations involving:

    • distances
    • coordinates
    • offsets
    • sizes
    • angles
    • movement

    Create a small library for the mathematics that is common across your exercises.

    You might end up with something like:

    raylib_template/
├── main.js
├── sketch.js
└── math.js

    The exact functions in math.js are up to you.

    The important thing is that you should not have the same useful calculation copied into several different programs.

    Instead:

    Exercise 1 ──┐
Exercise 2 ──┼──→ math.js
Exercise 3 ──┤
Exercise 4 ──┘

    You are now doing something programmers do all the time:

    taking code that works and reorganizing it so that it can be reused.

    When you are finished, look at all your exercises again.

    Ask yourself:

    If I started another Raylib exercise tomorrow, what code would I want to copy?

    That code probably belongs in the template or in one of your libraries.

    And ask:

    What code is specific to this particular exercise?

    That code belongs in sketch.js.

    The goal is not to create as many files as possible.

    The goal is to put each piece of code in a place where it makes sense and can be reused when it should be.
