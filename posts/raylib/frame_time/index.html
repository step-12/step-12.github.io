      Movement and Frame Time

      October 26, 2026
      Raylib, Frame-Time, Movement

      Is the dinosaur always this fast?#

      In the fourth part of The Long Run, we gave the dinosaur a velocity and gravity.

      Your code may look different, but somewhere it probably does something like this:

      dino.velocityY -= dino.gravity;
dino.y -= dino.velocityY;

      The velocity changes on every update. The position changes on every update too.

      This produces a jump, but there is a problem hiding in it.

      Try this before reading further#

      Find this line in your game:

      r.SetTargetFPS(60);

      Run the game and watch one complete jump.

      Now change the target to:

      r.SetTargetFPS(30);

      Run the game again.

      Then try:

      r.SetTargetFPS(120);

      Do not change the velocity or gravity yet.

      Does your game work the same at all three frame rates?

      Pause here and verify it in your own game.

      Eleven pixels per what?#

      Suppose your jump begins with this velocity:

      dino.velocityY = 11;

      And the position changes like this:

      dino.y -= dino.velocityY;

      What does 11 mean?

      It means:

      Move the dinosaur upward by 11 pixels on this update.

      At 30 FPS, update() runs about 30 times in one second.

      At 120 FPS, it runs about 120 times in one second.

      Ignore gravity for a moment and look only at what this velocity does:

      Frame rateMovement on each frameFrames in one secondMovement in one second
      30 FPS11 pixels30330 pixels
      60 FPS11 pixels60660 pixels
      120 FPS11 pixels1201320 pixels

      The game at 120 FPS changes the dinosaur’s position and velocity four times as often as the game at 30 FPS.

      This is frame-dependent movement. The movement depends on how many frames the computer produces.

      If velocity and gravity change once per frame, changing the number of frames changes the whole jump.

      Does every frame take the same time?#

      No.

      SetTargetFPS(60) tells Raylib what frame rate we would like. It is a target, not a promise.

      One frame may take a little longer because the computer has more work to do. Another computer may be faster or slower. A player may also choose a different target frame rate.

      Our game should move according to how much time has passed, not according to how many frames were drawn.

      Instead of describing the jump velocity in pixels per frame, we can describe it in pixels per second.

      Now we need to know how much of a second passed during one frame.

      GetFrameTime()#

      Raylib gives us:

      r.GetFrameTime();

      GetFrameTime() returns the time taken by the previous frame, in seconds.

      At about 60 FPS, it will be close to:

      0.0167 seconds

      At about 30 FPS, it will be close to:

      0.0333 seconds

      We can store it in a variable:

      const dt = r.GetFrameTime();

      dt means the change in time. You may also see it called frameTime or deltaTime.

      A small change to your jump#

      Let us change only one value as an example.

      Suppose your current vertical velocity is:

      dino.velocityY = 11;

      What does 11 mean in the current program?

      If you use it like this:

      dino.y -= dino.velocityY;

      it means that the dinosaur moves upward by 11 pixels on every frame.

      At 60 FPS, there are about 60 frames in one second:

      11 pixels per frame × 60 frames = 660 pixels per second

      So the same velocity written as a value per second is:

      dino.velocityY = 660;

      Now use only the part of that velocity that belongs to the current frame:

      dino.y -= dino.velocityY * dt;

      This follows a familiar relation:

      distance = speed × time

      For our jump:

      vertical movement = vertical velocity × frame time

      dt is the time for this frame. We subtract the movement from y because smaller y values move the dinosaur upward on the screen.

      At about 60 FPS, dt is close to 0.0167:

      660 × 0.0167 ≈ 11 pixels

      The movement looks familiar at 60 FPS, but the value now describes pixels per second rather than pixels per frame.

      Look at what happens at the other frame rates:

      Frame rateApproximate dtCalculation for one frameMovement on each frameMovement in one second
      30 FPS0.0333 seconds660 × 0.0333about 22 pixelsabout 660 pixels
      60 FPS0.0167 seconds660 × 0.0167about 11 pixelsabout 660 pixels
      120 FPS0.0083 seconds660 × 0.0083about 5.5 pixelsabout 660 pixels

      Without dt, every frame moves by the same 11 pixels, so more frames create more movement.

      With dt, a shorter frame receives a smaller movement and a longer frame receives a larger movement. After one second, the total is approximately the same.

      We have ignored gravity in these two tables so that we can see the effect of dt on one value clearly. The complete jump also changes velocity using gravity.

      The numbers need to change too#

      We converted the velocity from 11 pixels per frame to 660 pixels per second.

      Now suppose the old gravity is:

      gravity: 0.6,

      Before reading further, think about these questions:

      • Does gravity also need to change?
      • What does 0.6 mean in your current update?
      • What does gravity change?

      Pause and think about your answer.

      Gravity changes the velocity. In the old code, it changes the velocity by 0.6 on every frame.

      Our velocity is no longer measured per frame. It is now measured per second. Therefore, gravity must change too.

      Let us convert it one step at a time for a jump that worked at 60 FPS.

      Step 1: How much does gravity change the old velocity in one second?#

      Gravity reduces the upward velocity by 0.6 on each frame. There are 60 frames in one second:

      0.6 × 60 frames = 36

      After one second, the old velocity has changed by 36 pixels per frame.

      Step 2: Convert that velocity change into pixels per second#

      We have already changed velocity from pixels per frame to pixels per second. So convert 36 in the same way:

      36 pixels per frame × 60 frames = 2160 pixels per second

      Therefore, during one second, gravity changes the new velocity by 2160 pixels per second.

      That is why the complete calculation contains two 60s:

      0.6 × 60 × 60 = 2160
      • The first 60 accounts for gravity being applied on 60 frames in one second.
      • The second 60 converts the changed velocity from pixels per frame to pixels per second.

      The new gravity is:

      gravity: 2160,

      Use dt when gravity changes the velocity:

      dino.velocityY -= dino.gravity * dt;

      This uses the same idea:

      change in velocity = gravity × time

      Here, dt is again the amount of time that passed during this frame.

      So our two converted values are:

      jumpVelocity: 660,
gravity: 2160,

      Apply this to your jump#

      Write down:

      • your current jump velocity
      • your current gravity and
      • the FPS at which your jump currently works.

      Then calculate the new velocity and gravity for your game.

      Use your calculated values with dt, run the game at different frame rates, and verify that it works the same.

      If you are unsure what one of your current values means, stop and ask. Explain what the value changes on each update. Work out its unit before deciding how to convert it.

      What should use dt?#

      Use dt when a value describes a change over time:

      dino.y -= velocityY * dt;
velocityY -= gravity * dt;

      Do not add it to everything.

      The size of the dinosaur does not depend on time:

      dino.width = 40;

      A key press does not need to be multiplied by time either:

      if (r.IsKeyPressed(r.KEY_SPACE)) {
  dino.velocityY = dino.jumpVelocity;
}

      The key press starts the jump. The movement that follows happens over time.

      Verify it again#

      After changing the jump, repeat the first experiment.

      Run the game at:

      r.SetTargetFPS(30);
r.SetTargetFPS(60);
r.SetTargetFPS(120);

      Verify that your game works the same at all three frame rates.

      The number of frames will change, but the movement should remain the same. This is frame-independent movement.
