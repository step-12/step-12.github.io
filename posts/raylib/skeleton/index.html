    Raylib, Organization

    Organizing a Raylib Program#

    You have now written a few small Raylib programs.

    You have probably noticed that even a small program starts to contain several different kinds of code:

    • code that prepares the window
    • code that changes things
    • code that draws things
    • code that keeps the program running

    It is useful to give these different responsibilities a little structure.

    We are going to use the following skeleton:

    function setup() {}

function update() {}

function draw() {}

function loop() {
  update();
  draw();
}

function main() {
  setup();
  loop();
}

main();

    This is not a rule imposed by Raylib.

    It is a way for us to organize our thinking.

    Setup#

    setup() is where we prepare the program.

    For example:

    function setup() {
  r.InitWindow(screenWidth, screenHeight, "Center rectangle");
  r.SetTargetFPS(FPS);
}

    The window needs to exist before we can draw into it.

    The frame rate needs to be configured before the program starts running.

    These are things that happen once.

    So they belong in setup().

    Notice that setup() does not contain the main loop.

    It prepares the world. It does not run the world.

    The Loop#

    The program then enters its loop:

    function loop() {
  while (!r.WindowShouldClose()) {
    update();
    draw();
  }
}

    There are two things happening repeatedly:

    update();
draw();

    First, we update our program.

    Then, we draw what the program currently looks like.

    This distinction is important.

    For the moment, our update() function can be completely empty:

    function update() {}

    That might seem unnecessary.

    Why have a function that does nothing?

    Because we are establishing a structure for the program.

    Something will eventually need to change.

    Representation and Drawing#

    Consider the rectangle from the previous exercise.

    We have:

    const screenWidth = 400;
const screenHeight = 400;

const rectWidth = 200;
const rectHeight = 200;

    These values are a representation of something in our program.

    They describe the rectangle.

    The drawing code takes that representation and turns it into pixels:

    function draw() {
  const rectX = calcOffset(screenWidth, rectWidth);
  const rectY = calcOffset(screenHeight, rectHeight);

  r.BeginDrawing();
  r.ClearBackground(r.BLACK);
  r.DrawRectangle(rectX, rectY, rectWidth, rectHeight, r.WHITE);
  r.EndDrawing();
}

    The rectangle’s width and height are part of the state of our program.

    The drawing function looks at that state and asks:

    Given what the program currently knows, what should I put on the screen?

    This is one of the ideas we want to keep developing.

    The state of the program and its representation on the screen are not the same thing.

    The rectangle can exist as numbers:

    width = 200
height = 200

    without being drawn.

    Drawing is something we do with that representation.

    Update#

    Now uncomment these lines from the earlier exercise:

    // rectWidth++;
// rectHeight--;

    and change the declarations:

    let rectWidth = 200;
let rectHeight = 200;

    We can put the changes into update():

    function update() {
  rectWidth++;
  rectHeight--;
}

    Now the program has two separate jobs.

    update() changes the representation:

    function update() {
  rectWidth++;
  rectHeight--;
}

    draw() looks at the representation:

    function draw() {
  const rectX = calcOffset(screenWidth, rectWidth);
  const rectY = calcOffset(screenHeight, rectHeight);

  r.BeginDrawing();
  r.ClearBackground(r.BLACK);
  r.DrawRectangle(rectX, rectY, rectWidth, rectHeight, r.WHITE);
  r.EndDrawing();
}

    The loop connects the two:

    while (!r.WindowShouldClose()) {
  update();
  draw();
}

    Something changes.

    Then we show the result of that change.

    Then it changes again.

    Then we show the new result.

    And so on.

    This is the basic shape of a great many programs that deal with things changing over time.

    Why Keep Them Separate?#

    Imagine putting everything into draw():

    function draw() {
  rectWidth++;
  rectHeight--;

  // draw...
}

    It might work.

    But now the function that is supposed to describe what the program looks like is also responsible for changing what the program is.

    That makes it harder to reason about.

    Instead, we can ask two different questions:

    Update:

    What has changed?

    Draw:

    Given the current state, what should be displayed?

    These are different questions.

    Keeping them separate gives each function a smaller responsibility.

    As our programs become more complicated, this distinction becomes increasingly useful.

    Functions and Global Variables#

    There is another thing worth noticing in our draw() function.

    It uses these variables:

    screenWidth;
screenHeight;
rectWidth;
rectHeight;

    without receiving them as arguments.

    For example, we could have written:

    function draw(width, height) {
  // ...
}

    and passed everything the function needs to it.

    In general, this is a good direction for functions.

    A function is easier to understand when you can look at its arguments and know what information it needs.

    For example:

    function calcOffset(x1, x2) {
  return (x1 - x2) / 2;
}

    You do not need to know anything else about the program to understand this function.

    Give it two numbers.

    It gives you a number back.

    That is a useful property.

    An Exception for Now#

    Our draw() function is different.

    It is deliberately using the variables outside itself:

    function draw() {
  const rectX = calcOffset(screenWidth, rectWidth);
  const rectY = calcOffset(screenHeight, rectHeight);

  // ...
}

    We are allowing this for now because it makes the structure of these early Raylib programs easier to see.

    The program’s state is sitting outside the functions, and draw() is reading that state.

    This is an exception to an idea we will be developing.

    Eventually, we will work toward programs where our functions do not quietly depend on global variables.

    We will have to think carefully about what information a function needs and how that information gets to it.

    That is a problem worth solving.

    For now, do not solve it.

    Notice it.

    A Skeleton for Our Programs#

    For the programs we are writing now, think of this as our basic skeleton:

    function setup() {
  // prepare things
}

function update() {
  // change the state
}

function draw() {
  // display the current state
}

function loop() {
  while (!r.WindowShouldClose()) {
    update();
    draw();
  }
}

function main() {
  setup();
  loop();
}

main();

    There is a useful rhythm here:

    setup
  ↓
update → draw
  ↑      ↓
  └──────┘

    setup() happens once.

    update() and draw() happen repeatedly.

    The update changes the representation.

    The draw observes that representation.

    This gives us a place to put new ideas as our programs become more interesting.

    Separating the Program#

    There is one more change we will eventually make.

    Right now, everything is sitting in one file:

    program.js

    That is convenient while our programs are small.

    It will not remain convenient forever.

    Eventually, we will separate the code responsible for our program’s setup, update, and draw from the code responsible for running it.

    The exact arrangement is something we will discover as the programs grow.

    For now, pay attention to the boundaries we have created.

    We have separated:

    • preparation
    • updating
    • drawing
    • looping

    Those boundaries are more important than the files they happen to live in.

    The files will come later.

    Keep Experimenting#

    Take all of your existing programs and reorganize it using this skeleton.

    Do not add new behaviour.

    Just move the existing code into setup(), update(), and draw().

    Then ask yourself:

    • What information does each function need?
    • Which values represent the state of the program?
    • Which code changes those values?
    • Which code only reads them?
    • Which functions are depending on variables they did not receive as arguments?
    • Is each function doing one clear job?

    You are not trying to make the program clever.

    You are trying to make its structure easier to see.

    That is a useful habit to develop as programs get larger.
