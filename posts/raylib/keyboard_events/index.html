      Keyboard Events

      October 22, 2026
      Raylib, Keyboard, Interaction

      Can we play yet?#

      We can draw a rectangle. We can change its colour. We can even make it move across the screen.

      Now imagine watching that rectangle move from left to right. Again. And again.

      It might be interesting for a little while.

      But there is nothing for us to do. Whatever we press, the rectangle continues with its very important rectangle business.

      That gets boring.

      Think about a game you enjoy. What would happen if you could no longer control anything? The player runs by itself, jumps by itself, and wins or loses without your help.

      Would you still feel like you were playing?

      Something changes when we can take part. We choose when to move. We try to avoid something. We make a mistake and try again.

      Our choices affect what happens next.

      That is interaction.

      Let’s give our rectangle some.

      Move when I ask you to#

      We already know how to move something:

      player.x += 4;

      Put this in update(), and the player moves every time the function runs.

      But what if we want it to move only when we press the right arrow?

      We need an if. And we need something to ask about the keyboard.

      Raylib gives us this:

      r.IsKeyPressed(r.KEY_RIGHT);

      This asks whether the right arrow has just been pressed. The answer is true or false.

      So, inside update(), we can write:

      if (r.IsKeyPressed(r.KEY_RIGHT)) {
  player.x += 4;
}

      Use the sketch you already have. Keep drawing your player as before, and try this change in its update step. Make sure the Raylib window is selected when you press the keys.

      Press the right arrow. Release it. Press it again.

      The rectangle moves when you ask it to.

      We have not changed how rectangles are drawn. We have changed when their position changes.

      What happened when we pressed the key?#

      Your finger pushed a key down.

      That is something that happened. We call such an occurrence an event.

      Releasing the key is another event. Clicking a mouse button is an event too.

      But our program is busy going around its loop, updating and drawing. What if it is drawing at the moment you press the key?

      Does it have to stop everything immediately?

      No. The operating system receives the keyboard input, and Raylib collects it as part of its normal frame loop.

      Raylib keeps track of which keys are down. It also records key presses in a small temporary waiting area called a key buffer.

      Think of it as a short list of presses waiting to be read.

      Can we see what is waiting?

      Raylib gives us GetKeyPressed(). Each call takes the next key code from the buffer. If nothing is waiting, it returns 0.

      Try this inside update():

      const key = r.GetKeyPressed();

if (key !== 0) {
  console.log(key);
}

      Press A. Then B. Then the right arrow. Look at the terminal.

      The numbers identify the keys you pressed. To recognise one of them, try:

      console.log(r.KEY_A);

      Compare that number with the one you get when you press A.

      What if two presses are waiting when our update runs?

      Suppose Raylib collected A, then B. The first call to GetKeyPressed() gives us A’s code and removes it from the buffer. The next call gives us B’s code. A further call returns 0.

      We can keep reading until nothing is left:

      let key = r.GetKeyPressed();

while (key !== 0) {
  console.log(key);
  key = r.GetKeyPressed();
}

      Use this in place of the first experiment. Each trip through the loop reads one waiting press.

      The buffer holds presses collected for the current frame. Raylib clears the old queue when it collects input for the next frame, so it does not remember every key pressed since the program started.

      There is a useful difference between our two questions:

      • IsKeyPressed(r.KEY_RIGHT) asks whether a particular key was newly pressed. It does not remove anything from the buffer.
      • GetKeyPressed() takes the next waiting key code from the buffer. For our rectangle, we already know which key matters, so let’s keep using IsKeyPressed().

      Our code can then ask about the input during update(). If the right arrow was pressed, our if changes player.x.

      The next drawing shows the player at its new position.

      The key does not move the rectangle directly. Our code connects the press to the movement.

      What if we keep holding it?#

      Go back to this:

      if (r.IsKeyPressed(r.KEY_RIGHT)) {
  player.x += 4;
}

      Press the right arrow and keep holding it.

      The rectangle takes one step. Then it stops.

      Why?

      We pressed the key once. Keeping our finger on it does not make IsKeyPressed() report a new press on every frame.

      But for movement, we want to keep moving for as long as the key is down.

      That is a different question:

      if (r.IsKeyDown(r.KEY_RIGHT)) {
  player.x += 4;
}

      Try holding the key now.

      On each update, the key is still down, so we move again. When we release it, the condition becomes false and the movement stops.

      Pressed asks about the start of the action. Down asks about its continuing state.

      Try them side by side#

      Use these two checks in update():

      if (r.IsKeyPressed(r.KEY_RIGHT)) {
  player.x += 20;
}

if (r.IsKeyDown(r.KEY_DOWN)) {
  player.y += 4;
}

      Hold Right. Then hold Down. Then hold both.

      Which one takes a single step? Which one keeps moving?

      Try tapping each key quickly as well.

      A quick tap is still a press followed by a release. Holding the key simply leaves more time between those two events.

      And when we let go?#

      We have looked at the beginning of a press and the time spent holding the key.

      What about the end?

      Raylib gives us another question:

      r.IsKeyReleased(r.KEY_SPACE);

      Let’s make a press and a release do different things. Put this in update():

      if (r.IsKeyPressed(r.KEY_SPACE)) {
  player.color = r.RED;
}

if (r.IsKeyReleased(r.KEY_SPACE)) {
  player.color = r.BLUE;
}

      Use player.color as the colour when drawing your rectangle:

      r.DrawRectangleRec(player, player.color);

      Press Space. Hold it. Release it.

      The rectangle becomes red when you press and blue when you release.

      Why does it stay red while you hold Space?

      Because player.color still contains r.RED. A brief event can cause a change that lasts.

      We can now describe the life of a key press:

      What happensWhat we can ask
      You push the key downHas it just been pressed?
      You keep holding itIs it down?
      You let goHas it just been released?
      You leave it aloneIs it up?

      The four functions are:

      r.IsKeyPressed(r.KEY_SPACE);
r.IsKeyDown(r.KEY_SPACE);
r.IsKeyReleased(r.KEY_SPACE);
r.IsKeyUp(r.KEY_SPACE);

      IsKeyUp() is true whenever the key is not down, including when you have never touched it. IsKeyReleased() is true for the frame in which Raylib reports the release.

      On the frame of a new press, IsKeyPressed() and IsKeyDown() can both be true. The key has just been pressed, and it is now down.

      From an event to a response#

      Let’s step back and follow what happened.

      1. You pressed Space.
      2. The operating system received the keyboard input.
      3. Raylib collected the input and kept information about it.
      4. Our update() checked whether Space had been pressed.
      5. Our code changed player.color.
      6. The next drawing showed the new colour.

      We can call this the event life cycle: something happens, the program receives information about it, and our code decides how to respond.

      Notice that receiving an event and responding to it are different steps.

      What if we press Space, but have no code that checks it?

      The input can still reach Raylib. But our rectangle has no reason to change colour. We have not told it what that press should do.

      What if we change the response?

      if (r.IsKeyPressed(r.KEY_SPACE)) {
  player.x = 100;
}

      Now the same key press changes the position instead of the colour.

      The event tells us what happened. Our code gives it meaning.

      This idea applies beyond the keyboard. A mouse button is clicked, the program receives the input, and some code responds. A window is resized, the program receives that information, and some code adjusts the layout.

      The details change, but we can keep asking the same questions:

      • What happened?
      • How does our program find out?
      • What should it do in response?

      For keyboard input, there is one more useful question: are we responding to the press, the time spent holding the key, or the release?

      That is why we needed more than one keyboard function.

      What about A, B, C, and the number keys?#

      We have been giving Raylib names such as r.KEY_RIGHT and r.KEY_SPACE.

      There are names for letters and numbers too:

      r.KEY_A;
r.KEY_B;
r.KEY_C;
r.KEY_ONE;
r.KEY_TWO;
r.KEY_THREE;

      These are properties on r, just like r.RED. Their values identify the keys.

      We can combine a key name with whichever question we need:

      if (r.IsKeyPressed(r.KEY_A)) {
  player.color = r.RED;
}

if (r.IsKeyDown(r.KEY_D)) {
  player.x += 4;
}

      Press A to change colour. Hold D to move right.

      The key name chooses which key. The function chooses what we ask about it.

      Use r.KEY_A for this check, rather than the string "a". Checking a game control and reading typed text are different jobs.

      Can two keys work together?#

      Try this:

      if (r.IsKeyDown(r.KEY_RIGHT)) {
  player.x += 4;
}

if (r.IsKeyDown(r.KEY_DOWN)) {
  player.y += 4;
}

      Hold Right and Down together.

      Both conditions can be true. Both coordinates change. The player moves diagonally.

      What would happen if we used else if for the second condition?

      It would only be checked when the first condition was false. Our player would no longer respond to both directions together in the same update.

      Two keys being down does not force us to choose one. Our conditions decide what happens.

      What does Shift change?#

      Suppose we want Shift + Right to move the player faster.

      Shift is a modifier key. We often hold it to change what another key does. Control and Alt are other examples.

      Let’s choose a movement amount based on Shift:

      let step = 4;

if (r.IsKeyDown(r.KEY_LEFT_SHIFT)) {
  step = 8;
}

if (r.IsKeyDown(r.KEY_RIGHT)) {
  player.x += step;
}

      Keep this in update(), so step is chosen again on each update.

      Hold Right. While still holding it, press Shift. Then release Shift.

      The movement becomes faster and then returns to its usual amount.

      What if someone uses the Shift key on the other side?

      We can allow either one:

      const shiftDown =
  r.IsKeyDown(r.KEY_LEFT_SHIFT) ||
  r.IsKeyDown(r.KEY_RIGHT_SHIFT);

      Use shiftDown as the condition when choosing step. || means either Shift is enough.

      Hold one, press another#

      Now suppose Shift + R should put the rectangle back at its starting position.

      Using the same shiftDown value, we can write:

      if (shiftDown && r.IsKeyPressed(r.KEY_R)) {
  player.x = 100;
  player.y = 200;
}

      This asks two things: is Shift down, and has R just been pressed?

      && means both must be true.

      Why not use IsKeyPressed() for Shift too?

      Because we normally hold Shift first and press R afterwards. We do not want to require both new presses to happen in the same frame.

      Try it in the other order: hold R first, then press Shift. Why does the reset not happen then?

      How do we find the other names?#

      We have used only a few keys and functions. How do we find the others?

      We can ask our tools to show us.

      In VS Code#

      In a file where we have imported Raylib as r, type r..

      Look at the suggestions. These are names available on r.

      There may be quite a few. We can narrow them down by typing more.

      Try r.KEY_ to look for key names. Try r.IsKey to look for functions that check a key.

      Use the arrow keys to move through the suggestions. Press Tab or Enter to accept one. If the suggestions do not appear, try Control + Space.

      For example, suppose we want to check whether a key was released. Start typing r.IsKey and look for a name that matches that question.

      We do not need to know every name before we begin. Suggestions help us discover what is available.

      In the terminal#

      From your Raylib project directory, start the Node.js terminal:

      node

      Load the package:

      const r = require("raylib");

      Now type r. and press Tab. Press Tab again if needed to display the available names.

      Try typing r.KEY_ or r.IsKey, then pressing Tab. The extra characters help narrow the suggestions.

      This works in the interactive Node.js terminal.

      Try finding a key we have not used yet. Then use it to change the rectangle’s colour or position.

      Start with something you want to do. Look at the suggestions. Find a tool that might help, and try it.

      From a question to code#

      When we want a program to respond to an event, start by describing the behaviour in ordinary words.

      For example:

      Move the player right while the right arrow is held down.

      Before writing code, ask:

      • What input matters? The right arrow.
      • When should we respond? On every update while it is down.
      • What should change? The player’s horizontal position.

      Each answer gives us a piece of the code:

      if (r.IsKeyDown(r.KEY_RIGHT)) {
  player.x += 4;
}

      Now change the sentence:

      Turn the player red when A is pressed.

      The input changes. The moment we care about changes. The response changes too.

      if (r.IsKeyPressed(r.KEY_A)) {
  player.color = r.RED;
}

      Sometimes we need one more question:

      Does anything else need to be true?

      For Shift + R, Shift must already be down when R is pressed. That gives us two conditions joined with &&.

      There is a useful habit here: describe the behaviour first, then turn each part into code.

      The event tells us what happened. The conditions decide whether we should respond. The code inside the if makes the change.

      Try it#

      Give your rectangle three controls:

      • Hold the arrow keys to move.
      • Press 1, 2, or 3 to choose a colour.
      • Hold either Shift and press R to return to the starting position.

      For each control, first describe what should happen in a sentence. Then ask: which key matters, and should we respond when it is pressed, while it stays down, or when it is released? Check whether anything else needs to be true, and decide which value should change. Use these answers to write your condition and its response.

      Then try your controls. Tap. Hold. Release. Combine two keys.

      The rectangle is still a rectangle. But now you have something to do with it.
