    Recursion Assignments#

    For these assignments, you do not need to learn anything new about JavaScript. Use the things you already know: functions, parameters, return values, strings, numbers, conditionals, and basic operators.

    There are three small problems.

    1. Nested Parentheses#

    Write a function that takes a number n and returns a string containing n pairs of nested parentheses.

    For example:

    5 → "((((()))))"

    There are five opening parentheses followed by five closing parentheses.

    Some more examples:

    0 → ""
1 → "()"
2 → "(())"
3 → "((()))"
4 → "(((())))"

    Your function should work for any non-negative integer n.

    For example:

    parentheses(3)
// "((()))"

parentheses(5)
// "((((()))))"

    Think about it#

    What should the function return when n is 0?

    Once you know that, ask yourself:

    If I already know how to make n - 1 pairs of parentheses, how could I use that to make n pairs?

    Your solution must use recursion.

    Make sure your function returns a value and doesn’t simply console.log the value!

    2. The Growing and Shrinking Pattern#

    Write a function that takes a number n and produces a pattern of stars.

    For n = 3, the result should be:

    *
**
***
**
*

    For n = 4:

    *
**
***
****
***
**
*

    For n = 1:

    *

    And for n = 0, the result should be an empty string.

    The function should return one string containing newline characters.

    For example:

    pattern(3)
// "*\n**\n***\n**\n*"

    Make sure your function returns a value and doesn’t simply console.log the value!

    3. The Two Spacecraft#

    You are travelling through a strange region of space where ships do not travel in straight lines.

    Instead, they follow fixed routes through a sequence of gates.

    There are two routes.

    The first route is:

    Aurora → Ember → Nebula → Rift → Aurora → ...

    The second route is:

    Ember → Nebula → Rift → Obsidian → Eclipse → Ember → ...

    Each ship moves one gate forward on every move.

    The first ship starts at Aurora.

    The second ship starts at Ember.

    So at the beginning:

    Ship 1: Aurora
Ship 2: Ember

    After one move:

    Ship 1: Ember
Ship 2: Nebula

    After two moves:

    Ship 1: Nebula
Ship 2: Rift

    And so on.

    Eventually, the two ships will be at the same gate at the same time.

    Your job is to find how many moves it takes for them to meet.

    Your function#

    Write a function that takes the two starting positions and returns the number of moves until the two ships are at the same gate.

    For example, with the routes above:

    meet("Aurora", "Ember")

    should return:

    ?

    You must work out the answer.

    The function should also work when the starting positions are different.

    For example:

    meet("Rift", "Obsidian")

    and

    meet("Nebula", "Eclipse")

    should each produce the correct number of moves.

    Important detail#

    The two ships move at the same time.

    A move means that both ships advance by one position.

    You are not looking for the first time either ship visits the other’s gate. You are looking for the first time:

    ship 1's current gate === ship 2's current gate

    after both have made the same number of moves.

    The routes#

    Treat these as cycles. When a ship reaches the end of its route, it goes back to the beginning.

    First route:

    Aurora → Ember → Nebula → Rift → Aurora → ...

    Second route:

    Ember → Nebula → Rift → Obsidian → Eclipse → Ember → ...

    Your solution must use recursion. Do not use a for or while loop to repeatedly move the ships.

    Recursion — Solutions#

    In the previous post, you were given three problems to solve using recursion.

    There is a useful way to think about all three of them:

    Solve a smaller version of the problem, then use that answer to construct the larger answer.

    This is the basic pattern we will follow.

    For every recursive function, we want to identify two things:

    1. The smallest problem we can solve directly.
    2. How to construct a larger problem from a smaller problem.

    Let’s look at the three problems again.

    1. Parentheses#

    We wanted:

    parentheses(0) → ""
parentheses(1) → "()"
parentheses(2) → "(())"
parentheses(3) → "((()))"
parentheses(4) → "(((())))"

    Look closely at these answers.

    For parentheses(2):

    (())

    We can see it as three pieces:

    ( + () + )

    But () is exactly:

    parentheses(1)

    So:

    parentheses(2)
    = "(" + parentheses(1) + ")"

    Now look at parentheses(3):

    ((()))

    Again, we can decompose it:

    ( + (()) + )

    And (()) is:

    parentheses(2)

    So:

    parentheses(3)
    = "(" + parentheses(2) + ")"

    The same thing works for every value of n.

    parentheses(n)
    = "(" + parentheses(n - 1) + ")"

    We have decomposed the problem.

    Now we need to compose the answer.

    function parentheses(n) {
  return n <= 0
    ? ""
    : "(" + parentheses(n - 1) + ")";
}

    There is also a very important question here:

    When should we stop?

    Eventually we reach:

    parentheses(0)

    There is nothing inside the parentheses, so the answer is simply:

    ""

    That is our base case.

    We can now trace the function:

    parentheses(3)

"(" + parentheses(2) + ")"

"(" + "(" + parentheses(1) + ")" + ")"

"(" + "(" + "(" + parentheses(0) + ")" + ")" + ")"

"(" + "(" + "(" + "" + ")" + ")" + ")"

"((()))"

    Notice what happened.

    We did not tell the computer how to construct all three pairs at once.

    We told it:

    To make n pairs, make one pair around the answer for n - 1.

    That is decomposition followed by composition.

    2. The Pattern#

    Our second problem was to produce:

    *
**
***
**
*

    for n = 3.

    There are several ways to think about this problem.

    Let’s start by looking at just the individual lines.

    We can write a small function that produces a line of stars:

    function stars(n) {
  return n <= 0 ? "" : "*" + stars(n - 1);
}

    Again, notice the decomposition.

    For example:

    stars(3)
    = "*" + stars(2)
    = "*" + "*" + stars(1)
    = "*" + "*" + "*" + stars(0)
    = "***"

    So now we have a useful building block.

    We can think of our pattern as three pieces:

    *
**
***
**
*

    The middle line is the largest line.

    Everything before it grows toward that line, and everything after it shrinks away from it.

    One way to express that directly is:

    function pattern(n, i) {
  const line = stars(i);

  if (i >= n) return line;

  return line + "\n"
       + pattern(n, i + 1) + "\n"
       + line;
}

    We start with:

    pattern(5, 1)

    The i parameter tells us which line we are currently constructing.

    For example:

    pattern(5, 1)

    can be decomposed into:

    stars(1)
+
pattern(5, 2)
+
stars(1)

    Then pattern(5, 2) becomes:

    stars(2)
+
pattern(5, 3)
+
stars(2)

    And so on.

    Eventually:

    pattern(5, 5)

    is simply:

    *****

    The recursion then returns, composing the complete answer as it goes.

    A useful helper#

    There is something slightly awkward about this version.

    We keep writing:

    line + "\n" + something + "\n" + line

    We can extract that operation into its own function:

    function join(a, b, c) {
  const NEWLINE = "\n";
  return a + NEWLINE + b + NEWLINE + c;
}

    Now our recursive function becomes:

    function pattern(n, i) {
  const line = stars(i);

  if (i >= n) return line;

  return join(line, pattern(n, i + 1), line);
}

    The recursive idea is now easier to see:

    Put the current line above and below the smaller pattern.

    The join function is not doing anything fundamentally new. It merely gives a name to an operation we were already performing.

    That is often a useful thing to do when programming.

    If you see the same piece of logic appearing repeatedly, you can give that logic a name.

    Another way to solve the pattern#

    There is another interesting decomposition.

    Instead of keeping track of which line we are on, we can make the string of stars itself part of the recursive state.

    function pattern(n, stars) {
  if (n <= 1) return stars;

  return stars
    + "\n"
    + pattern(n - 1, stars + "*")
    + "\n"
    + stars;
}

    We would start with:

    pattern(5, "*")

    Let’s decompose this.

    The first call is:

    pattern(5, "*")

    which becomes:

    "*"
+
pattern(4, "**")
+
"*"

    Then:

    pattern(4, "**")

    becomes:

    "**"
+
pattern(3, "***")
+
"**"

    And eventually:

    pattern(1, "*****")

    returns:

    "*****"

    The recursion then composes the answer on the way back out.

    Comparing the two#

    The two solutions are solving the same problem, but they represent the problem differently.

    The first version says:

    pattern(n, i)

    where i means:

    “Which line am I currently working on?”

    The second says:

    pattern(n, stars)

    where stars means:

    “What should the current line look like?”

    Neither representation is inherently correct or incorrect.

    The first separates two ideas:

    How many lines?
Which line?

    and uses stars() to construct the line.

    The second carries the already-constructed line through the recursion.

    This gives us a useful programming lesson:

    The way you represent the state of a problem can change the shape of the solution.

    The second version is shorter and has fewer moving parts. The first version separates the two concerns more explicitly and gives us a reusable stars() function.

    There is a tradeoff between simplicity of the final code and how explicitly the different pieces of the problem are represented.

    3. The Two Spacecraft#

    Our final problem involved two spacecraft travelling around different routes.

    The first route was:

    Aurora → Ember → Nebula → Rift → Aurora → ...

    The second route was:

    Ember → Nebula → Rift → Obsidian → Eclipse → Ember → ...

    We want to know how many moves it takes until both spacecraft are at the same gate.

    The key observation is surprisingly simple.

    Suppose the ships are currently here:

    Ship 1: Ember
Ship 2: Rift

    After one move, they will be here:

    Ship 1: Nebula
Ship 2: Obsidian

    So the larger problem can be decomposed into:

    Move both ships once, then solve the same problem again.

    That gives us:

    meet(Ember, Rift)

= 1 + meet(Nebula, Obsidian)

    And if they are already at the same gate:

    meet(Nebula, Nebula)

    the answer is simply:

    0

    That gives us the recursive structure:

    function meet(gate1, gate2) {
  return gate1 === gate2
    ? 0
    : 1 + meet(
        nextGateOnRoute1(gate1),
        nextGateOnRoute2(gate2)
      );
}

    The decomposition is:

    meet(current positions)

    ↓

move both ships

    ↓

meet(new positions)

    The composition is:

    1 + answer for the smaller problem

    Again:

    Solve the smaller problem, then use its answer to solve the larger problem.

    Making the composition easier to read#

    The code above works, but the recursive call is a little difficult to read:

    1 + meet(
  nextGateOnRoute1(gate1),
  nextGateOnRoute2(gate2)
)

    We can make the structure more obvious by giving another operation a name.

    Suppose we want a function that combines three pieces of text with newlines:

    function join(a, b, c) {
  return a + "\n" + b + "\n" + c;
}

    Then:

    join("hello", "world", "!")

    produces:

    hello
world
!

    The function is useful because it hides an uninteresting detail.

    Instead of repeatedly writing:

    a + "\n" + b + "\n" + c

    we can simply write:

    join(a, b, c)

    The same idea appeared in the second problem.

    Extracting a function#

    Suppose we initially wrote our pattern like this:

    return line + "\n"
     + pattern(n, i + 1) + "\n"
     + line;

    We can look at that and notice:

    a + "\n" + b + "\n" + c

    is an operation in its own right.

    So we extract it:

    function join(a, b, c) {
  return a + "\n" + b + "\n" + c;
}

    and now write:

    return join(line, pattern(n, i + 1), line);

    This is called composition.

    We are building a larger operation out of smaller operations.

    Can join be made smaller?#

    Look at our three-argument version:

    function join(a, b, c) {
  return a + "\n" + b + "\n" + c;
}

    There is another way to see this.

    What does join(a, b, c) really do?

    It joins a and b, and then joins that result with c.

    So perhaps join itself can be defined using a smaller join.

    Let’s make join take only two arguments:

    function join(a, b) {
  return a + "\n" + b;
}

    Now we can compose it:

    join(join(a, b), c)

    The inner call:

    join(a, b)

    produces:

    a
b

    Then the outer call:

    join(join(a, b), c)

    produces:

    a
b
c

    So our original three-argument operation:

    join(a, b, c)

    can instead be expressed as:

    join(join(a, b), c)

    This is a small example of an important idea:

    Large operations can be constructed by composing smaller operations.

    We have seen the same idea three times now.

    For parentheses:

    "(" + parentheses(n - 1) + ")"

    For the pattern:

    join(line, smallerPattern, line)

    And for joining:

    join(join(a, b), c)

    Putting the ideas together#

    Recursion can initially feel like a strange trick:

    “A function calls itself.”

    But that is not really the interesting part.

    The interesting question is:

    What smaller version of this problem can I solve?

    For the parentheses problem:

    parentheses(n)
    ↓
parentheses(n - 1)

    For the pattern:

    pattern(n)
    ↓
smaller pattern

    For the spacecraft:

    meet(current positions)
    ↓
meet(after one move)

    Then ask:

    How do I use the smaller answer to construct the larger answer?

    That is the second half of recursion.

    You are repeatedly doing two things:

    DECOMPOSE
   ↓
find a smaller problem

COMPOSE
   ↓
use its answer to construct the current answer

    Once you start seeing problems this way, recursion becomes less mysterious.

    It becomes a way of describing a problem in terms of itself, but smaller.
